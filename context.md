# Kontext: claude-cli

## Zweck

Persönliches CLI-Tool in TypeScript, wird als eigenständige ausführbare Datei `cl` nach `~/.local/bin` deployed.

## Architektur-Entscheidungen

- **Runtime/Module:** Node.js (ESM, `"type": "module"`), TypeScript-Target `ES2023`, `module`/`moduleResolution: NodeNext`.
- **TypeScript-Version:** `^6.0.3` statt der neuesten `7.x` – TypeScript 7 ist der neue native (Go-basierte) Compiler-Rewrite, `typescript-eslint@8` unterstützt ihn noch nicht (Peer-Dep verlangt `<6.1.0`). Sobald `typescript-eslint` TS7 unterstützt, kann angehoben werden.
- **CLI-Framework:** `commander` (Argument-Parsing, `--help`/`--version` automatisch generiert).
- **Dev ohne Compile:** `tsx` führt `src/index.ts` direkt aus.
- **Compile:** `tsc` – volles Type-Checking, Ausgabe nach `dist/` (ESM, referenziert `node_modules` normal).
- **Deploy-Bündelung:** `esbuild` bündelt `dist/index.js` inkl. aller Dependencies (z. B. `commander`) in eine einzelne Datei, da am Zielort `~/.local/bin` kein `node_modules` existiert. `tsc` allein reicht für das Deployment nicht aus.
- **Versionierung:** `src/version.ts` wird vor `dev`/`build` aus `package.json` generiert (`scripts/generate-version.mjs`, via npm `pre`-Hooks). Datei ist generiert und daher in `.gitignore`. Grund: ein direkter JSON-Import von `package.json` würde nach dem Deploy als Einzeldatei zur Laufzeit fehlschlagen (keine `package.json` neben `cl` in `~/.local/bin`).
- **Config/Context-System:** `config.json` (Root) hat fünf Felder: `main` (ein `AgentDefinition`-Objekt `{ description: string, contexts: string[], model: string }`, ohne `name`), `agents` (Array von benannten `AgentConfig`-Objekten `{ name: string, description: string, contexts: string[], model: string }`), `databaseDirectory: string` (Verzeichnis fuer die SQLite-Datenbank von `cl server`, aktuell `/home/simon/commands`), `paths: PathEntry[]` (Array von `{ name: string, path: string, hosted?: HostedEntry[] }`, benannte Arbeitsverzeichnisse fuer `cl server`, siehe unten) und `tasks: TaskConfig[]` (Array von benannten `TaskDefinition`-Objekten `{ name: string, description: string, contexts: string[], model: string, startCommand: string }`, siehe Task-System-Punkt unten – strukturell wie `agents`, nur zusätzlich mit `startCommand` und ausschließlich per `cl task <name>` erreichbar, nie über `cl server`). `HostedEntry` ist `{ name: string, path: string, type: "path" | "file" }` – benannte Datei-/Verzeichnis-Freigaben innerhalb eines Pfad-Eintrags, ueber `GET /files/...` abrufbar (siehe `cl server`-Eintrag unten). `HostedEntry.path` ist **relativ zum `path` des umgebenden `PathEntry`** (nicht absolut) – aufgeloest per `join(entry.path, hosted.path)` in `resolveHostedEntry()`. Jeder Context-Name löst zu einer Markdown-Datei unter `contexts/` auf, z. B. `"main"` → `contexts/main.md`, `"dev/tools"` → `contexts/dev/tools.md`. `src/config.ts` (`loadConfig()`, `resolveAgent(name)`, `resolveContext(name)`, `resolvePathEntry(config, name)`, `resolvePath(config, name)`, `listPathNames(config)`, `listHostedNames(config, pathName)`, `resolveHostedEntry(config, pathName, hostedName)`) liest bevorzugt die lokal liegenden Dateien (`config.json`/`contexts/*.md`, relativ zum Repo-Root über `import.meta.url` aufgelöst) und fällt zurück auf `EMBEDDED_CONFIG`/`EMBEDDED_CONTEXTS` aus `src/generated/embedded-context.ts`, falls die lokalen Dateien fehlen (Fall des deployten Einzeldatei-Binaries ohne begleitende `config.json`/`contexts/`). `resolvePathEntry(config, name)` sucht im übergebenen `config.paths` nach `name` und liefert den vollen `PathEntry` (wirft, falls kein Eintrag existiert); `resolvePath(config, name)` ist ein duenner Wrapper darum, der nur `.path` liefert – beide nehmen bewusst `config` als Parameter (statt intern `loadConfig()` aufzurufen, wie `resolveAgent`/`resolveContext` es tun), damit z. B. `cl server --paths-file` einen überschriebenen `Config`-Wert durchreichen kann; `listPathNames(config)` liefert nur die Namen (`paths[].name`), ohne die Pfade. `listHostedNames(config, pathName)` liefert `(entry.hosted ?? []).map(h => h.name)` (wirft wie `resolvePathEntry`, falls `pathName` unbekannt); `listHostedSummaries(config, pathName)` ist das Pendant fuer `GET /manifest` – liefert `{ name, type }[]` statt nur Namen (also inkl. `type`, aber weiterhin **ohne** Dateisystem-Pfad); `resolveHostedEntry(config, pathName, hostedName)` liefert den `HostedEntry` mit **bereits aufgeloestem absolutem** `path` (`{ ...hosted, path: join(entry.path, hosted.path) }` – wirft zusaetzlich, falls `hostedName` in diesem Pfad-Eintrag nicht existiert). `src/server.ts` nutzt also immer den von `resolveHostedEntry()` gelieferten absoluten Pfad, nie das rohe `hosted.path` aus der Config direkt. `src/generated/embedded-context.ts` wird vor `dev`/`build` aus `config.json` + allen `contexts/**/*.md` generiert (`scripts/generate-context-bundle.mjs`, via npm `pre`-Hooks), ist generiert und in `.gitignore`. Dadurch ist das Ergebnis jedes Builds (inkl. `esbuild`-Bundle) unabhängig vom Ausführungsort funktionsfähig.
- **`paths`-Override per Datei (`cl server --paths-file <file>`):** `-P, --paths-file <file>` auf dem `server`-Subcommand (`src/index.ts`) liest eine externe JSON-Datei, die nur den `paths`-Teil enthält (Form `{ "paths": PathEntry[] }`, identisch zum `paths`-Feld in `config.json`), und ersetzt damit `config.json`s `paths` vollständig für diesen Serverlauf – ohne `config.json` selbst zu ändern. `loadPathsOverride(filePath)` (`src/config.ts`) liest die Datei per `readFileSync` (Pfad relativ zu `process.cwd()`, **nicht** repo-relativ wie `config.json`/`contexts/`, da es eine externe, vom Nutzer angegebene Datei ist) und validiert den Inhalt über `parsePathsOverride(raw)` (wirft bei fehlendem/fehlerhaftem `paths`-Feld). `applyPathsOverride(config, paths)` gibt eine Kopie von `config` mit ersetztem `paths`-Array zurück. `src/index.ts`s `server`-Action ruft bei gesetzter Option `startServer(applyPathsOverride(loadConfig(), loadPathsOverride(file)), port)` auf; Fehler beim Lesen/Parsen brechen den Start mit Fehlermeldung + Exit-Code 1 ab, statt den Server zu starten. Damit diese überschriebene `Config` auch bei `GET /paths` und den POST-Routen (`resolvePath`) wirkt, nimmt `src/server.ts`s `handleGetPaths`/`handlePostCommand`/`handleRequest` `config: Config` explizit als Parameter (aus `startServer(config, port)`s Closure durchgereicht) statt intern `loadConfig()` neu zu laden.
- **Agent-Start (`cl [agent]`):** `src/index.ts` deklariert ein optionales positionales Argument `[agent]` via `commander` und ruft im `.action()`-Handler `launchAgent(agent)` auf. `resolveAgent(name)` in `src/config.ts` gibt bei `name === undefined` `config.main` zurück, sonst den Eintrag aus `config.agents` mit passendem `name` (Fehler, falls nicht gefunden). `src/launch.ts` (`launchAgent(name)`) baut aus den `contexts` der aufgelösten `AgentDefinition` den System-Prompt (Inhalte verkettet mit `\n\n`) und startet `claude` (Claude Code CLI) per `child_process.spawn` mit `stdio: 'inherit'` (voll interaktiv im Vordergrund, kein `--print`). Flags: `--model <agent.model>`, `--append-system-prompt <systemPrompt>`, `--permission-mode auto` (fest verdrahtet in `buildClaudeArgs()`, siehe unten – jede von `cl` gestartete `claude`-Session laeuft im Auto-Mode, ohne Rueckfragen). `cl` ohne Argument → `main`-Agent; `cl <name>` → benannter Agent aus `agents[]`; `--help`/`--version` laufen weiterhin über `commander` (eager options, vor der Action).
- **Dynamisches `--help`:** `src/index.ts` liest bei jedem `--help`-Aufruf per `commander`s `.addHelpText('after', () => ...)` live `loadConfig()` und listet alle Moeglichkeiten aus `config.json` auf – kein Codeausbau noetig, wenn `config.json` neue Eintraege bekommt. Gemeinsame Helfer: `formatConfigHelp(kind, render)` (faengt Config-Fehler ab und zeigt statt Crash einen Fehlertext im Abschnitt) und `formatConfigSection(title, entries: AgentSummary[], emptyText)` (Spaltenausrichtung, Hinweis bei leerer Liste). Darauf bauen auf: `formatAgentsHelp()` (`listAgents()`, `cl`/`cl <name>`), `formatTasksHelp()` (`listTasks()` aus `src/config.ts`, `cl task <name>`), `formatServerAgentsHelp()` (`POST /`, `POST /<agent>`) und `formatPathsHelp()` (pro `paths[]`-Eintrag Commands als `POST /paths/<name>/commands/<key>  <displayName>: <description>` und Hosted-Eintraege als `GET /files/<name>/<hosted>  (type)`). Zuordnung: Root-`--help` → Agents + Model-Override + Tasks; jeder Model-Subcommand → Agents; `task --help` → Tasks; `server --help` → Agent-Endpunkte + Pfade.
- **Model-Subcommands (`cl <model> [agent]`):** `MODEL_COMMANDS` (`haiku`/`h`, `sonnet`/`s`, `opus`/`o`, `fable`/`f`) ist in `src/config.ts` definiert (Single Source of Truth, von `src/index.ts` importiert). `src/index.ts` registriert pro Eintrag ein `program.command(name).alias(alias)` mit demselben `[agent]`-Argument wie der Root-Command; die Action ruft `launchAgent(agent, modelName)` auf. `commander` erlaubt Root-Action und benannte Subcommands parallel: matcht das erste Positional-Token einen Subcommand-Namen/Alias, wird dieser dispatcht, sonst greift die Root-Action (empirisch mit der installierten `commander`-Version verifiziert). `launchAgent(name, modelOverride?)` in `src/launch.ts` nutzt `modelOverride ?? agent.model` – überschreibt also gezielt nur das Model aus `config.json`, alles andere (Contexts, Auto-Mode) bleibt unverändert.
- **Reservierte Agent-Namen (Startup-Crash):** `src/config.ts` (`assertNoReservedAgentNames()`, aufgerufen aus `parseConfig()` – also bei jedem `loadConfig()`) wirft einen Fehler, falls ein `agents[].name` mit einem `MODEL_COMMANDS`-Namen/Kurzform (`haiku`, `h`, `sonnet`, `s`, `opus`, `o`, `fable`, `f`) **oder** `"server"` (`RESERVED_COMMAND_NAMES`) kollidiert. Damit ein solcher Konflikt die CLI unabhängig vom Aufruf (`--help`, `--version`, ohne Argumente, jeder Subcommand) sofort abbrechen laesst, ruft `src/index.ts` `loadConfig()` zusätzlich **eager auf Modulebene** auf (vor `program.parseAsync()`) und beendet den Prozess bei Fehler synchron mit `process.exit(1)`.
- **Headless-Modus (`-h, --headless [prompt]`):** Kollidiert per Definition mit der `-h`-Kurzform von `--help` – daher `program.helpOption('--help', ...)` **ohne** `-h`; nur das lange `--help` zeigt noch Hilfe, `-h` ist ausschließlich `--headless`. Die Option ist sowohl auf dem Root-Command als auch auf jedem der vier Model-Subcommands separat registriert (`.option(HEADLESS_OPTION_FLAGS, ...)`), da `commander` Custom-Options nicht automatisch an Subcommands vererbt. Root-Command hat zusätzlich `.enablePositionalOptions()`: ohne das griff bei Aufrufen wie `cl sonnet mainagent -h 'text'` fälschlich (empirisch reproduziert) die Root-Options-Definition, sodass der Wert von `-h` im Subcommand verlorenging (`headless` blieb `undefined` statt des Strings) – mit `enablePositionalOptions()` parst jeder Command-Level seine Optionen unabhängig vom übergeordneten. `[prompt]` (eckige Klammern) macht den Options-Wert optional: `-h` allein → `options.headless === true`; `-h 'text'` → `options.headless === 'text'`; Flag ganz weggelassen → `undefined` (empirisch mit der installierten `commander`-Version verifiziert). `resolveHeadlessPrompt()` in `src/index.ts` behandelt `true` durch interaktives Abfragen via `node:readline/promises` (`rl.question('Prompt: ')` auf `process.stdin`/`process.stdout`), gibt Strings direkt zurück, `undefined` bleibt `undefined`. `launchAgent(name, modelOverride?, headlessPrompt?)` in `src/launch.ts` hängt bei gesetztem `headlessPrompt` `--print <headlessPrompt>` an die `claude`-Argumente an (Claude Codes Non-Interactive-Modus); ohne `-h` bleibt der Aufruf wie bisher voll interaktiv (`stdio: 'inherit'`, kein `--print`).
- **Task-System (`cl task <name>`, immer interaktiv, CLI-only, immer Auto-Mode):** `TaskDefinition` (`src/config.ts`) ist strukturell wie `AgentDefinition` (`{ description, contexts, model }`), zusaetzlich mit Pflichtfeld `startCommand: string` (nicht-leer, per `isTaskDefinition()` validiert). `runTask(task)` (`src/launch.ts`) baut den System-Prompt wie bei Agents (`buildSystemPrompt()`) und ruft `buildClaudeArgs(model, systemPrompt, undefined, task.startCommand)` auf – der vierte Parameter `interactivePrompt` wird (nur wenn kein `headlessPrompt` gesetzt ist) als reines positionales Argument angehaengt, **ohne** `--print`. Die echte `claude`-CLI startet bei einem positionalen Prompt ohne `--print` per Definition interaktiv und schickt diesen Prompt automatisch als erste Nachricht ab (verifiziert per `claude --help`: "starts an interactive session by default") – exakt aequivalent dazu, den Text selbst einzutippen und abzuschicken. `buildClaudeArgs()` haengt `--permission-mode auto` fest an (kein Parameter mehr, keine Konfigurationsmoeglichkeit – gilt seit dem "jede Session immer Auto-Mode"-Umbau fuer alle Aufrufer: `launchAgent()`/`runHeadlessCommand()`/`runTask()`/`runFixAgent()` in `src/gradle-install.ts`). `spawn('claude', args, { stdio: 'inherit' })` laeuft synchron im Vordergrund, `cl task <name>` kennt bewusst **keine** Optionen (kein `-d`, kein `-h`, kein sonstiger Modus). **Tasks sind nie ueber `cl server`/die HTTP-API erreichbar** – kein `/task`-Endpunkt, kein `tasks`-Feld in `GET /manifest` (HTTP-Requests haben kein TTY, eine interaktive Session ist darueber nicht sinnvoll nutzbar).
- **`cl server` (`src/server.ts`):** `node:http`-Server (kein Framework) mit zehn Routen: `POST /` (main-Agent), `POST /:agent` (benannter Agent), `GET /state/:id`, `GET /paths`, `GET /manifest`, `GET /files/:pathName`, `GET /files/:pathName/:hostedName`, `GET /files/:pathName/:hostedName/:fileName`, `GET /health` (kein Auth), `GET /auth/status` (nur Lokalnetz, kein `X-TOTP-Code`) – dazu die beiden Setup-Routen (`POST /auth/setup`, `POST /auth/setup/confirm`). Kein `/task`-Endpunkt – Tasks sind bewusst CLI-only (siehe Task-System-Punkt unten). Beide Command-POST-Routen erwarten JSON-Body `{ command: string, path: string, model?: string }`, sind **immer headless** (nutzen `runHeadlessCommand()` aus `src/launch.ts`, das per `--print` startet und `stdout`/`stderr` per `stdio: ['ignore', 'pipe', 'pipe']` abfaengt statt `stdio: 'inherit'`). `path` ist Pflicht (400 falls fehlend/leer) und referenziert per Name einen Eintrag in `config.json`s `paths[]` (aufgeloest via `resolvePath(name)` aus `src/config.ts`, 404 falls unbekannt) – der zugehoerige Dateisystem-Pfad wird als `cwd` an `runHeadlessCommand()` durchgereicht (der `claude`-Prozess laeuft also in diesem Verzeichnis), nie der Pfad selbst im Request. Beide POST-Routen generieren eine `crypto.randomUUID()`-ID, legen sofort eine `t_commands`-Zeile mit `status: 'running'` (inkl. aufgeloestem `path`) an und antworten **sofort** mit `202 { id }` – der `claude`-Prozess laeuft im Hintergrund weiter, jeder Output-Chunk aktualisiert die `output`-Spalte live (voller bisheriger Output pro Update, kein Diff/Append-SQL). Bei Prozessende wird `status` auf `completed`/`failed` gesetzt (Exit-Code 0 → completed) und `exit_code` gespeichert; bei Spawn-Fehler (z. B. `claude` nicht im PATH) `status: 'failed'` mit der Fehlermeldung als `output`. `GET /state/:id` liest die Zeile direkt (404 falls unbekannt), inkl. `path`-Feld. `GET /paths` liefert `{ paths: string[] }` – nur die Namen aus `config.paths` (`listPathNames()`), nicht die Dateisystem-Pfade. `GET /manifest` liefert die aggregierte Gesamtsicht aus Agents/Paths inkl. Commands/Hosted-Eintraegen (siehe eigener Punkt unten).
  - **`GET /files/:pathName`** (`handleGetHostedNames`) liefert `{ hosted: string[] }` – nur die Namen aus `paths[].hosted` des per `pathName` aufgeloesten Eintrags (`listHostedNames()`, 404 falls `pathName` unbekannt).
  - **`GET /files/:pathName/:hostedName`** (`handleGetHostedEntry`) loest den `HostedEntry` per `resolveHostedEntry()` auf (404 falls `pathName`/`hostedName` unbekannt). Bei `type: "file"`: prueft `existsSync`+`isFile()` (404 falls die Datei nicht mehr existiert), dann `sendFileDownload()` (streamt per `createReadStream().pipe(res)`, `Content-Type` aus einer kleinen eingebauten `extname()`→MIME-Tabelle (`MIME_TYPES`, Fallback `application/octet-stream`), `Content-Disposition: attachment; filename="<basename>"`, `Content-Length` aus `statSync`). Bei `type: "path"`: prueft `existsSync`+`isDirectory()` (404 falls nicht mehr vorhanden), listet dann per `readdirSync(path, { withFileTypes: true })` **nur direkte Dateien** (`dirent.isFile()`, keine Unterordner, nicht rekursiv) als `{ files: string[] }`.
  - **`GET /files/:pathName/:hostedName/:fileName`** (`handleGetHostedFile`) nur gueltig wenn der `HostedEntry` `type: "path"` ist (sonst 404 – ein `type: "file"`-Eintrag hat keine Unterdateien); baut `filePath = resolve(join(resolve(entry.path), fileName))` und verifiziert **vor** jedem Dateizugriff, dass `filePath` innerhalb des Verzeichnisses liegt (`filePath === directory || filePath.startsWith(directory + sep)`, sonst `400`) – Pfad-Traversal-Schutz. Ueber Node's `new URL()`-Parsing (WHATWG-Dot-Segment-Removal) kann ein `..`-Segment ohnehin nie unveraendert als eigenes URL-Segment beim Server ankommen (empirisch verifiziert), die Pruefung ist bewusstes Defense-in-Depth fuer diesen Datei-Download-Endpunkt und kein toter Code fuer ein unmoegliches Szenario. Danach `existsSync`+`isFile()`-Check (404) und `sendFileDownload()` wie oben.

- **`GET /manifest`:** liefert in einem Aufruf die gesamte per `config.json` gesteuerte Oberflaeche als aggregiertes JSON – gedacht als Grundlage fuer eine spaetere, voll dynamische Remote-Steuerung (z. B. per App), ohne dass diese die Struktur von `config.json` kennen muss. Antwort: `{ agents: { command, description }[], paths: { name, commands: PathCommandEntry[], hosted: { name, type }[] }[] }` – **keine** Tasks (bewusst, siehe Task-System-Punkt unten). `agents` ist `listAgents(config)` (identisch zum `--help`-Text), `paths` kombiniert pro Pfad `listPathCommands()` (volle Command-Definitionen inkl. `command`-String) mit `listHostedSummaries()` (**nur** `name`+`type`, keine Dateisystem-Pfade – wie bei allen anderen Endpunkten wird der reale Pfad nie exposed). `listHostedSummaries(config, pathName)` (`src/config.ts`) ist das hosted-Pendant zu `listPathCommands()`, wirft wie `resolvePathEntry()` bei unbekanntem `pathName`. Kein Ersatz fuer die bestehenden Detail-Endpunkte (`GET /paths/:pathName/commands`, `GET /files/:pathName`), sondern eine zusaetzliche gebuendelte Sicht fuer UIs, die alle Moeglichkeiten auf einen Schlag anzeigen wollen.

  Jeder Request (Erfolg wie Fehler, GET wie POST) wird zusaetzlich in `t_access_log` protokolliert (Methode, Pfad, finaler Status-Code, bei POST der rohe Body-Text) – das ist eine eigene Tabelle, getrennt von `t_commands`. `-p, --port` (Default `8787`) steuert den Listen-Port; `SIGINT`/`SIGTERM` schliessen Server und DB sauber. Der Prozess läuft im Vordergrund (kein Daemonizing – die offene Listening-Socket hält den Node-Event-Loop ohnehin am Leben). Beim Start (`server.listen`-Callback) druckt `printEndpoints()` einmalig alle Endpunkte auf stdout (`GET /health`, `POST /auth/setup`, `POST /auth/setup/confirm`, `GET /auth/status`, `POST /`, `POST /<agent>` je Eintrag aus `config.agents`, `GET /state/:id`, `GET /paths`, `GET /manifest`, `GET /paths/:pathName/commands`, `POST /paths/<pathName>/commands/<key>` je konfiguriertem Command, `GET /files/:pathName`, `GET /files/:pathName/:hostedName`, `GET /files/:pathName/:hostedName/:fileName`) – die erste Zeile bleibt bewusst exakt `"Endpunkte:"` (ohne Zusatz dahinter), da Tests per `stdout.includes('Endpunkte:')` auf Server-Bereitschaft warten; ein zusaetzlicher Hinweistext steht in einer eigenen Zeile danach. Danach loggt `handleRequest()` jeden einzelnen Request zusätzlich zum DB-Eintrag auch auf stdout (`<ISO-Timestamp> <METHOD> <path> -> <statusCode>`).

- **Google-Authenticator-Schutz (TOTP) fuer `cl server`:** Alle Endpunkte ausser `GET /health`, `POST /auth/setup`, `POST /auth/setup/confirm` und `GET /auth/status` verlangen einen gueltigen 6-stelligen TOTP-Code (RFC 6238, SHA1, 30s-Schritt) im Header `X-TOTP-Code` (`isRequestAuthorized()` in `src/server.ts`, geprueft in `handleRequest()` **vor** jedem Routing ausser fuer den `auth`-Praefix); ohne konfigurierten/bestaetigten Authenticator liefern alle geschuetzten Routen `401`. `src/totp.ts` (keine externe Dependency, nur `node:crypto`) implementiert Base32-En-/Decoding, `generateSecret()` (20 zufaellige Bytes → 32-Zeichen-Base32 ohne Padding), `generateTotp()`/`verifyTotp()` (Zeitfenster-Toleranz ±1 Schritt fuer Uhr-Drift, `timingSafeEqual`-Vergleich) und `buildOtpAuthUrl()` (otpauth://-URI fuer QR-Import). Bewusst **keine Replay-Sperre** pro einzelnem Code – derselbe Code bleibt fuer alle Requests im selben 30s-Fenster gueltig, da TOTP hier als Zugriffsschranke fuer ein persoenliches Tool dient (nicht als Einmal-Login) und eine Replay-Sperre schnelle Folge-Requests mit demselben, noch gueltigen Code faelschlich blockieren wuerde.
  - **Setup-Endpunkte (`POST /auth/setup`, `POST /auth/setup/confirm`, `GET /auth/status`):** Nur aus dem lokalen Netz erreichbar, sonst `404` (identisch zu einer unbekannten Route) – geprueft ueber `isLocalNetworkAddress(req.socket.remoteAddress)` (`src/network.ts`, niemals ueber spoofbare Header wie `X-Forwarded-For`) gegen Loopback/RFC1918/IPv6-ULA/Link-Local. `POST /auth/setup` erzeugt ein neues unbestaetigtes Secret (`setPendingTotpSecret()`, ueberschreibt ein vorheriges unbestaetigtes Secret) und liefert `{ secret, otpauthUrl }`; `409` falls bereits ein Authenticator **aktiv** (bestaetigt) ist. `POST /auth/setup/confirm` (Body `{ code }`) prueft den Code gegen das ausstehende Secret und aktiviert es via `confirmTotpSecret()`; `401` bei falschem Code, `409` falls bereits aktiv. Es kann so **immer nur ein** Authenticator gleichzeitig aktiv sein (Singleton-Zeile `id = 1 CHECK` in `t_totp`, siehe `src/db.ts`). `GET /auth/status` (`handleGetAuthStatus()`) liest `getTotpSecret(db)` und liefert `{ active: totp?.confirmed ?? false, pending: totp !== undefined && !totp.confirmed }` – nie das Secret selbst; erlaubt Clients, den Pairing-Zustand zu erfragen, ohne blind `POST /auth/setup` zu versuchen und sich nur auf `409` zu verlassen.
  - **Entfernen ausschliesslich per CLI:** `cl totp remove` (`src/index.ts`, ruft `deleteTotpSecret()` aus `src/db.ts` direkt auf) ist **kein** HTTP-Endpunkt – absichtlich, damit ein Angreifer mit HTTP-Zugriff den aktiven Authenticator nicht selbst entfernen/ersetzen kann; das Entfernen erfordert Shell-Zugriff auf die Maschine.
  - `t_totp` (`src/db.ts`): Single-Row-Tabelle (`id INTEGER PRIMARY KEY CHECK (id = 1)`, `secret`, `confirmed`, `created_at`), `INSERT ... ON CONFLICT(id) DO UPDATE` in `setPendingTotpSecret()` ersetzt ein unbestaetigtes Secret atomar.
- **Pfad-Commands (`paths[].commands`):** Jeder `PathEntry` kann zusaetzlich `commands?: { key, command, displayName, description }[]` definieren (`src/config.ts`, `listPathCommands()`/`resolvePathCommand()`). `GET /paths/:pathName/commands` listet sie (404 falls `pathName` unbekannt); `POST /paths/:pathName/commands/:key` fuehrt `command` per `runShellCommand()` (`src/launch.ts`, `spawn(command, { shell: true, cwd })`) **im Dateisystem-Verzeichnis des Pfad-Eintrags** (`paths[].path`, nicht ein `hosted`-Unterpfad) aus (404 falls `pathName`/`key` unbekannt). Tracking/Status-Abfrage nutzt dieselbe `t_commands`-Tabelle wie Agent-Commands (`agent: "path-command:<pathName>:<key>"`, `model: "-"`, da kein LLM involviert ist) – `GET /state/:id` funktioniert dadurch identisch fuer beide Command-Arten.
- **SQLite via `node:sqlite` statt `better-sqlite3`:** `src/db.ts` nutzt Node's eingebautes `node:sqlite` (`DatabaseSync`, seit Node 22.5, in Node 24 ohne Flag/Warnung nutzbar, `@types/node` deckt es ab). Bewusst **nicht** `better-sqlite3` (obwohl populärer/reifer), weil das ein natives Addon (`.node`-Binary) ist, das `esbuild` nicht in die Single-File-`cl.bundle.js` inlinen kann – das haette die gesamte "ein deploytes File reicht"-Architektur gebrochen. `node:sqlite` bleibt im Bundle als externes `import`/`require('node:sqlite')` stehen und wird zur Laufzeit von Node selbst aufgeloest, unabhaengig vom Ausführungsort (empirisch verifiziert: Bundle enthaelt `node:sqlite` als String, keine gebündelten Binaries). WAL-Modus ist aktiviert (`PRAGMA journal_mode = WAL`). Tabellen: `t_access_log` (Autoincrement-ID, Timestamp, Method, Path, Status-Code, Body) und `t_commands` (UUID-PK, agent, model, command, path, status, output, exit_code, created_at, updated_at) – `path` ist der ueber `resolvePath()` aufgeloeste Dateisystem-Pfad (cwd des `claude`-Prozesses), nicht der im Request uebergebene Name.
- **`databaseDirectory` in `config.json`:** wird beim Serverstart via `mkdirSync(..., { recursive: true })` angelegt, falls nicht vorhanden; SQLite-Datei liegt als `commands.db` (+ `-wal`/`-shm` im WAL-Modus) darin. Wie alle anderen `config.json`-Felder lokal-first mit Embedded-Fallback aufgeloest (funktional identisch, da der Wert ohnehin nur ein String ist).
- **`cl inst`/`cl instr` (fest verdrahtet, weder `config.json` noch API):** Zwei zusätzliche `program.command(...)`-Registrierungen in `src/index.ts` (`inst`, `instr`, beide in `RESERVED_COMMAND_NAMES` in `src/config.ts` wie `server`/`task`/`totp`), Logik in `src/gradle-install.ts`. `buildAndInstall(buildType: 'debug' | 'release', cwd = process.cwd())`: laeuft in einer `for (;;)`-Schleife (1) `runGradleBuild(cwd, buildType)` – `spawn('./gradlew', [assembleDebug|assembleRelease], { cwd, stdio: ['ignore','pipe','pipe'] })`, jeder Output-Chunk wird sowohl live nach `process.stdout` durchgereicht als auch fuer die Auswertung gesammelt, liefert `{ exitCode, output }` (nie ein Throw bei Exit-Code ≠ 0 – das wird explizit ausgewertet); (2) `exitCode === 0 && !hasWarnings(output)` beendet die Schleife (`break`) und geht weiter zum Install; sonst wird `runFixAgent(cwd, message)` aufgerufen – `spawn('claude', buildClaudeArgs('sonnet', FIX_AGENT_SYSTEM_PROMPT, message), { cwd, stdio: 'inherit' })` (headless via `--print`, `--permission-mode auto` – wie bei jedem `buildClaudeArgs()`-Aufruf fest verdrahtet, kein Parameter mehr –, `message` enthaelt Grund + volle Build-Ausgabe), danach iteriert die Schleife erneut (Build erneut versuchen) – **keine Obergrenze**, laeuft so oft, bis ein Build fehler- und warnungsfrei durchlaeuft; ein Fehler beim Spawnen von `claude` (`error`-Event, z. B. nicht im PATH) wirft und bricht `buildAndInstall` komplett ab. `hasWarnings(output)` erkennt sowohl das Substring `warning` (case-insensitive) als auch Kotlinc-Zeilen der Form `^\s*w:\s` (Kotlinc schreibt keine Woerter wie "warning", sondern `w: <file>: <message>` pro Zeile). Nach der Schleife: (3) `findApk(cwd, buildType)` durchsucht rekursiv `**/build/outputs/apk/<buildType>/*.apk` ab `cwd` (versteckte Ordner übersprungen), wirft ohne Treffer; (4) `adb devices` (`parseAdbDevices(output)` sucht die Zeile `"List of devices attached"` als Anker und parst alle Folgezeilen als `<serial>\t<status>`); (5) pro gefundenem Serial zuerst `readDeviceName(serial)` (`adb -s <serial> shell getprop ro.product.model`, bei Fehler/leerer Ausgabe Fallback auf die Serial – wirft nie), dann `adb -s <serial> install -r <apk>` einzeln in einer `for`-Schleife mit `try/catch` – ein Fehlschlag auf einem Gerät wird geloggt (`console.error`, `Installation auf <name> (<serial>) fehlgeschlagen`), bricht die Schleife aber nicht ab, die übrigen Geräte werden trotzdem versucht; Erfolge werden in `installed: { serial, name }[]` gesammelt; (6) `console.log(formatInstallSummary(installed))` – `Installiert auf <n> Geraet|Geraeten: <name> (<serial>), …` bzw. `Auf keinem Geraet installiert.` `cl inst` → `buildAndInstall('debug')`, `cl instr` → `buildAndInstall('release')`, beide ohne Optionen. Getestet in `src/gradle-install.test.ts` (`parseAdbDevices`/`findApk` als reine/Dateisystem-Tests, `buildAndInstall` End-to-End gegen ein skriptbares Fake-`./gradlew`-Shellscript im Test-`cwd` (`src/test-support/mock-gradlew.ts`, `writeFakeGradlew(cwd, { buildType, steps })` – `steps` ist eine Sequenz `{ exitCode?, stdout?, createApk? }[]`, ein Eintrag pro Aufruf, der letzte wiederholt sich; Aufrufzaehler in einer State-Datei `.gradlew-call-count`, auslesbar via `readGradlewCallCount(cwd)`) + ein Fake-`adb`-Shellscript im `PATH` (`src/test-support/mock-adb.ts`, `createMockAdb()` – loggt alle Aufrufe in eine Datei, `devicesOutput`/`failSerials`/`deviceNames` (Serial → Name fuer `shell getprop ro.product.model`, unbekannte Serials liefern Exit 1) steuern das simulierte Verhalten) + das Fake-`claude`-Binary (`src/test-support/mock-claude.ts`, `createMockClaude({ logFile })` – optionales `logFile` protokolliert jeden Aufruf als JSON-Zeile, noetig weil `runFixAgent` mit `stdio: 'inherit'` spawnt und dessen stdout dadurch nicht im Testprozess abfangbar ist)) sowie zusätzlich per CLI-Subprozess in `src/index.test.ts` (`runCli()` unterstützt dafür jetzt auch eine `cwd`-Option). Tests, die pruefen, dass kein Fix-Agent verfuegbar ist, setzen `PATH` bewusst auf nur `[adb.binDir, '/usr/bin', '/bin']` (kein `claude` auffindbar, aber `/bin/sh`+`cat` fuer das Fake-`gradlew`-Script weiterhin nutzbar) statt der echten `PATH` – sonst koennte ein auf der Testmaschine echt installiertes `claude`-Binary faelschlich gefunden und aufgerufen werden.
- **Linting:** ESLint (Flat Config, `eslint.config.js`) mit `typescript-eslint` `strictTypeChecked` + `stylisticTypeChecked`, typisiert nur für `src/**/*.ts` (eigenes `project`). `eslint.config.js` und `scripts/*.mjs` laufen nur mit `js.configs.recommended` (kein Type-Checking nötig). Für `src/**/*.test.ts` ist zusätzlich `@typescript-eslint/no-floating-promises` deaktiviert (eigener Override-Block in `eslint.config.js`) – `node:test`s `test(name, fn)` gibt bewusst eine nicht ge-awaitete Promise zurück, die der Test-Runner selbst nachverfolgt.
- **Formatierung:** Prettier, per `eslint-config-prettier` von ESLint-Stylistik entkoppelt.
- **Tests (`node:test` + `tsx`, kein Vitest/Jest):** `npm test` = `tsx --test 'src/**/*.test.ts'` (via `pretest` laufen vorher `generate-version`/`generate-context-bundle`, da Tests `src/generated/embedded-context.ts` importieren). Bewusst kein zusätzliches Test-Framework – `node:test`/`node:assert` sind Node-Builtins (kein weiterer Dependency-Fussabdruck), `tsx` ist ohnehin schon Dev-Dependency und stript TypeScript direkt (kein separater Kompilierschritt fürs Testen). `node:test`s `mock.module()` ist in dieser Node-Version nicht zuverlässig nutzbar (empirisch geprüft) – daher **keine** Modul-Mocks, stattdessen drei Test-Strategien je nach Modul-Charakter:

  3. **Echte Subprozesse statt Mocks für alles, was `claude` spawnt:** `src/test-support/mock-claude.ts` (`createMockClaude()`) schreibt ein ausführbares Node-Script namens `claude` in ein Temp-Verzeichnis, das seine `argv` als JSON + Marker auf stdout schreibt (robust gegen Newlines/Anführungszeichen im System-Prompt, da JSON-serialisiert) und konfigurierbare Output-Chunks mit Delay + Exit-Code liefert; `pathWithMock()` haengt dessen Verzeichnis vorn an `PATH`. Damit sind `runHeadlessCommand()` (`src/launch.test.ts`), `cl server`s POST-Endpunkte (`src/server.test.ts`) und die volle CLI (`src/index.test.ts`, via `src/test-support/run-cli.ts` – spawnt `node_modules/.bin/tsx src/index.ts <args>` als echten Kindprozess) End-to-End getestet, ohne echte `claude`-Aufrufe/API-Kosten.
  - `src/db.ts` wird direkt gegen echte temporäre SQLite-Dateien getestet (kein Mock nötig, `node:sqlite` ist synchron und schnell).
  - `src/server.ts`: `startServer()` gibt (seit diesem Refactor) `{ port, ready, close() }` zurück statt `void` – `port` ist ein Getter auf den tatsächlich gebundenen Port (relevant bei `port: 0` fürs OS-Port-Assignment in Tests), `ready` resolved nach `server.listen()`, `close()` räumt Listener + DB sauber auf. Tests treffen den Server per echtem `fetch()`.
  - `src/index.ts` wird **nie direkt importiert** (weder in Tests noch sonstwo) – das Modul hat Top-Level-Seiteneffekte (eager `loadConfig()` mit `process.exit(1)`, `program.parseAsync(process.argv)`), ein Import würde also sofort die echte CLI-Logik gegen die Test-Runner-`argv` ausführen. Getestet ausschliesslich per Subprozess.
  - Nebenbei durch die Tests gefundener Bug: `cl server --port 0` wurde von der eigenen Validierung (`port <= 0`) abgelehnt, obwohl Port `0` ("beliebiger freier Port", OS-Konvention) gültig ist – Fix: `port < 0`.

**`Makefile`:** duenner Wrapper um alle `package.json`-Scripts (`make generate-version`, `make generate-context-bundle`, `make dev`, `make build`, `make deploy`, `make release`, `make test`, `make lint`, `make format`) – jedes Target ruft 1:1 `npm run <script>` (bzw. `npm test` fuer `test`) auf, keine eigene Logik. `pre*`-Hooks (`predev`/`prebuild`/`pretest`) sind nicht als eigene Targets abgebildet, da `npm` sie beim Aufruf des jeweiligen Haupt-Scripts ohnehin automatisch mitausfuehrt.

Release) in einer Schleife, die bei Build-Fehler oder Warnings in der Build-Ausgabe einen Claude-Sonnet-Fix-Agent im Auto-Mode (headless, `--print`) mit der Build-Ausgabe als Prompt startet und danach den Build erneut versucht – ohne Obergrenze, bis er fehler- und warnungsfrei durchlaeuft. Erst dann wird die entstandene APK auf allen per `adb devices` gefundenen Geraeten installiert; Installationsfehler auf einzelnen Geraeten werden abgefangen und die restlichen Geraete trotzdem versucht; jedes Geraet wird mit Namen (`getprop ro.product.model`) + Serial geloggt und am Ende eine Zusammenfassung ausgegeben, auf wie vielen und welchen Geraeten installiert wurde – `src/gradle-install.ts`, `src/index.ts`, `src/config.ts` (reservierte Namen).
