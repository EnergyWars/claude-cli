# Kontext: claude-cli

## Zweck

Persönliches CLI-Tool in TypeScript, wird als eigenständige ausführbare Datei `cl` nach `~/.local/bin` deployed.

## Architektur-Entscheidungen

- **Runtime/Module:** Node.js (ESM, `"type": "module"`), TypeScript-Target `ES2023`, `module`/`moduleResolution: NodeNext`.
- **TypeScript-Version:** `^6.0.3` statt der neuesten `7.x` – TypeScript 7 ist der neue native (Go-basierte) Compiler-Rewrite, `typescript-eslint@8` unterstützt ihn noch nicht (Peer-Dep verlangt `<6.1.0`). Sobald `typescript-eslint` TS7 unterstützt, kann angehoben werden.
- **CLI-Framework:** `commander` (Argument-Parsing, `--help`/`--version` automatisch generiert).
- **Dev ohne Compile:** `tsx` führt `src/index.ts` direkt aus.
- **Compile:** `tsc` – volles Type-Checking, Ausgabe nach `dist/` (ESM, referenziert `node_modules` normal).
- **Deploy-Bündelung:** `esbuild` bündelt `dist/index.js` inkl. aller Dependencies (z. B. `commander`) in eine einzelne Datei, da am Zielort `~/.local/bin` kein `node_modules` existiert. `tsc` allein reicht für das Deployment nicht aus.
- **Versionierung:** `src/version.ts` wird vor `dev`/`build` aus `package.json` generiert (`scripts/generate-version.mjs`, via npm `pre`-Hooks). Datei ist generiert und daher in `.gitignore`. Grund: ein direkter JSON-Import von `package.json` würde nach dem Deploy als Einzeldatei zur Laufzeit fehlschlagen (keine `package.json` neben `cl` in `~/.local/bin`).
- **Config/Context-System:** `config.json` (Root) hat vier Felder: `main` (ein `AgentDefinition`-Objekt `{ description: string, contexts: string[], model: string }`, ohne `name`), `agents` (Array von benannten `AgentConfig`-Objekten `{ name: string, description: string, contexts: string[], model: string }`), `databaseDirectory: string` (Verzeichnis fuer die SQLite-Datenbank von `cl server`, aktuell `/home/simon/commands`) und `paths: PathEntry[]` (Array von `{ name: string, path: string, hosted?: HostedEntry[] }`, benannte Arbeitsverzeichnisse fuer `cl server`, siehe unten). `HostedEntry` ist `{ name: string, path: string, type: "path" | "file" }` – benannte Datei-/Verzeichnis-Freigaben innerhalb eines Pfad-Eintrags, ueber `GET /files/...` abrufbar (siehe `cl server`-Eintrag unten). `HostedEntry.path` ist **relativ zum `path` des umgebenden `PathEntry`** (nicht absolut) – aufgeloest per `join(entry.path, hosted.path)` in `resolveHostedEntry()`. Jeder Context-Name löst zu einer Markdown-Datei unter `contexts/` auf, z. B. `"main"` → `contexts/main.md`, `"dev/tools"` → `contexts/dev/tools.md`. `src/config.ts` (`loadConfig()`, `resolveAgent(name)`, `resolveContext(name)`, `resolvePathEntry(config, name)`, `resolvePath(config, name)`, `listPathNames(config)`, `listHostedNames(config, pathName)`, `resolveHostedEntry(config, pathName, hostedName)`) liest bevorzugt die lokal liegenden Dateien (`config.json`/`contexts/*.md`, relativ zum Repo-Root über `import.meta.url` aufgelöst) und fällt zurück auf `EMBEDDED_CONFIG`/`EMBEDDED_CONTEXTS` aus `src/generated/embedded-context.ts`, falls die lokalen Dateien fehlen (Fall des deployten Einzeldatei-Binaries ohne begleitende `config.json`/`contexts/`). `resolvePathEntry(config, name)` sucht im übergebenen `config.paths` nach `name` und liefert den vollen `PathEntry` (wirft, falls kein Eintrag existiert); `resolvePath(config, name)` ist ein duenner Wrapper darum, der nur `.path` liefert – beide nehmen bewusst `config` als Parameter (statt intern `loadConfig()` aufzurufen, wie `resolveAgent`/`resolveContext` es tun), damit z. B. `cl server --paths-file` einen überschriebenen `Config`-Wert durchreichen kann; `listPathNames(config)` liefert nur die Namen (`paths[].name`), ohne die Pfade. `listHostedNames(config, pathName)` liefert `(entry.hosted ?? []).map(h => h.name)` (wirft wie `resolvePathEntry`, falls `pathName` unbekannt); `resolveHostedEntry(config, pathName, hostedName)` liefert den `HostedEntry` mit **bereits aufgeloestem absolutem** `path` (`{ ...hosted, path: join(entry.path, hosted.path) }` – wirft zusaetzlich, falls `hostedName` in diesem Pfad-Eintrag nicht existiert). `src/server.ts` nutzt also immer den von `resolveHostedEntry()` gelieferten absoluten Pfad, nie das rohe `hosted.path` aus der Config direkt. `src/generated/embedded-context.ts` wird vor `dev`/`build` aus `config.json` + allen `contexts/**/*.md` generiert (`scripts/generate-context-bundle.mjs`, via npm `pre`-Hooks), ist generiert und in `.gitignore`. Dadurch ist das Ergebnis jedes Builds (inkl. `esbuild`-Bundle) unabhängig vom Ausführungsort funktionsfähig.
- **`paths`-Override per Datei (`cl server --paths-file <file>`):** `-P, --paths-file <file>` auf dem `server`-Subcommand (`src/index.ts`) liest eine externe JSON-Datei, die nur den `paths`-Teil enthält (Form `{ "paths": PathEntry[] }`, identisch zum `paths`-Feld in `config.json`), und ersetzt damit `config.json`s `paths` vollständig für diesen Serverlauf – ohne `config.json` selbst zu ändern. `loadPathsOverride(filePath)` (`src/config.ts`) liest die Datei per `readFileSync` (Pfad relativ zu `process.cwd()`, **nicht** repo-relativ wie `config.json`/`contexts/`, da es eine externe, vom Nutzer angegebene Datei ist) und validiert den Inhalt über `parsePathsOverride(raw)` (wirft bei fehlendem/fehlerhaftem `paths`-Feld). `applyPathsOverride(config, paths)` gibt eine Kopie von `config` mit ersetztem `paths`-Array zurück. `src/index.ts`s `server`-Action ruft bei gesetzter Option `startServer(applyPathsOverride(loadConfig(), loadPathsOverride(file)), port)` auf; Fehler beim Lesen/Parsen brechen den Start mit Fehlermeldung + Exit-Code 1 ab, statt den Server zu starten. Damit diese überschriebene `Config` auch bei `GET /paths` und den POST-Routen (`resolvePath`) wirkt, nimmt `src/server.ts`s `handleGetPaths`/`handlePostCommand`/`handleRequest` `config: Config` explizit als Parameter (aus `startServer(config, port)`s Closure durchgereicht) statt intern `loadConfig()` neu zu laden.
- **Agent-Start (`cl [agent]`):** `src/index.ts` deklariert ein optionales positionales Argument `[agent]` via `commander` und ruft im `.action()`-Handler `launchAgent(agent)` auf. `resolveAgent(name)` in `src/config.ts` gibt bei `name === undefined` `config.main` zurück, sonst den Eintrag aus `config.agents` mit passendem `name` (Fehler, falls nicht gefunden). `src/launch.ts` (`launchAgent(name)`) baut aus den `contexts` der aufgelösten `AgentDefinition` den System-Prompt (Inhalte verkettet mit `\n\n`) und startet `claude` (Claude Code CLI) per `child_process.spawn` mit `stdio: 'inherit'` (voll interaktiv im Vordergrund, kein `--print`). Flags: `--model <agent.model>`, `--append-system-prompt <systemPrompt>`, `--permission-mode acceptEdits` (Read ist in Claude Code ohnehin promptlos; `acceptEdits` deckt Write/Edit ab, ohne z. B. Bash pauschal zu bypassen). `cl` ohne Argument → `main`-Agent; `cl <name>` → benannter Agent aus `agents[]`; `--help`/`--version` laufen weiterhin über `commander` (eager options, vor der Action).
- **Dynamisches `--help`:** `src/index.ts` (`formatAgentsHelp()`) liest bei jedem `--help`-Aufruf per `commander`s `.addHelpText('after', () => ...)` live `loadConfig()` + `listAgents(config)` (aus `src/config.ts`) und listet alle Agents (`cl`/`cl <name>`) mit ihrer `description` auf – kein Codeausbau noetig, wenn `config.json` einen neuen Agent bekommt. Bei ungueltiger `config.json` wird ein Fehlertext statt eines Crashs angezeigt.
- **Model-Subcommands (`cl <model> [agent]`):** `MODEL_COMMANDS` (`haiku`/`h`, `sonnet`/`s`, `opus`/`o`, `fable`/`f`) ist in `src/config.ts` definiert (Single Source of Truth, von `src/index.ts` importiert). `src/index.ts` registriert pro Eintrag ein `program.command(name).alias(alias)` mit demselben `[agent]`-Argument wie der Root-Command; die Action ruft `launchAgent(agent, modelName)` auf. `commander` erlaubt Root-Action und benannte Subcommands parallel: matcht das erste Positional-Token einen Subcommand-Namen/Alias, wird dieser dispatcht, sonst greift die Root-Action (empirisch mit der installierten `commander`-Version verifiziert). `launchAgent(name, modelOverride?)` in `src/launch.ts` nutzt `modelOverride ?? agent.model` – überschreibt also gezielt nur das Model aus `config.json`, alles andere (Contexts, `acceptEdits`) bleibt unverändert.
- **Reservierte Agent-Namen (Startup-Crash):** `src/config.ts` (`assertNoReservedAgentNames()`, aufgerufen aus `parseConfig()` – also bei jedem `loadConfig()`) wirft einen Fehler, falls ein `agents[].name` mit einem `MODEL_COMMANDS`-Namen/Kurzform (`haiku`, `h`, `sonnet`, `s`, `opus`, `o`, `fable`, `f`) **oder** `"server"` (`RESERVED_COMMAND_NAMES`) kollidiert. Damit ein solcher Konflikt die CLI unabhängig vom Aufruf (`--help`, `--version`, ohne Argumente, jeder Subcommand) sofort abbrechen laesst, ruft `src/index.ts` `loadConfig()` zusätzlich **eager auf Modulebene** auf (vor `program.parseAsync()`) und beendet den Prozess bei Fehler synchron mit `process.exit(1)`.
- **Headless-Modus (`-h, --headless [prompt]`):** Kollidiert per Definition mit der `-h`-Kurzform von `--help` – daher `program.helpOption('--help', ...)` **ohne** `-h`; nur das lange `--help` zeigt noch Hilfe, `-h` ist ausschließlich `--headless`. Die Option ist sowohl auf dem Root-Command als auch auf jedem der vier Model-Subcommands separat registriert (`.option(HEADLESS_OPTION_FLAGS, ...)`), da `commander` Custom-Options nicht automatisch an Subcommands vererbt. Root-Command hat zusätzlich `.enablePositionalOptions()`: ohne das griff bei Aufrufen wie `cl sonnet mainagent -h 'text'` fälschlich (empirisch reproduziert) die Root-Options-Definition, sodass der Wert von `-h` im Subcommand verlorenging (`headless` blieb `undefined` statt des Strings) – mit `enablePositionalOptions()` parst jeder Command-Level seine Optionen unabhängig vom übergeordneten. `[prompt]` (eckige Klammern) macht den Options-Wert optional: `-h` allein → `options.headless === true`; `-h 'text'` → `options.headless === 'text'`; Flag ganz weggelassen → `undefined` (empirisch mit der installierten `commander`-Version verifiziert). `resolveHeadlessPrompt()` in `src/index.ts` behandelt `true` durch interaktives Abfragen via `node:readline/promises` (`rl.question('Prompt: ')` auf `process.stdin`/`process.stdout`), gibt Strings direkt zurück, `undefined` bleibt `undefined`. `launchAgent(name, modelOverride?, headlessPrompt?)` in `src/launch.ts` hängt bei gesetztem `headlessPrompt` `--print <headlessPrompt>` an die `claude`-Argumente an (Claude Codes Non-Interactive-Modus); ohne `-h` bleibt der Aufruf wie bisher voll interaktiv (`stdio: 'inherit'`, kein `--print`).
- **`cl server` (`src/server.ts`):** `node:http`-Server (kein Framework) mit acht Routen: `POST /` (main-Agent), `POST /:agent` (benannter Agent), `POST /task/:task`, `GET /state/:id`, `GET /paths`, `GET /files/:pathName`, `GET /files/:pathName/:hostedName`, `GET /files/:pathName/:hostedName/:fileName`. Beide Command-POST-Routen erwarten JSON-Body `{ command: string, path: string, model?: string }`, sind **immer headless** (nutzen `runHeadlessCommand()` aus `src/launch.ts`, das per `--print` startet und `stdout`/`stderr` per `stdio: ['ignore', 'pipe', 'pipe']` abfaengt statt `stdio: 'inherit'`). `path` ist Pflicht (400 falls fehlend/leer) und referenziert per Name einen Eintrag in `config.json`s `paths[]` (aufgeloest via `resolvePath(name)` aus `src/config.ts`, 404 falls unbekannt) – der zugehoerige Dateisystem-Pfad wird als `cwd` an `runHeadlessCommand()` durchgereicht (der `claude`-Prozess laeuft also in diesem Verzeichnis), nie der Pfad selbst im Request. Beide POST-Routen generieren eine `crypto.randomUUID()`-ID, legen sofort eine `t_commands`-Zeile mit `status: 'running'` (inkl. aufgeloestem `path`) an und antworten **sofort** mit `202 { id }` – der `claude`-Prozess laeuft im Hintergrund weiter, jeder Output-Chunk aktualisiert die `output`-Spalte live (voller bisheriger Output pro Update, kein Diff/Append-SQL). Bei Prozessende wird `status` auf `completed`/`failed` gesetzt (Exit-Code 0 → completed) und `exit_code` gespeichert; bei Spawn-Fehler (z. B. `claude` nicht im PATH) `status: 'failed'` mit der Fehlermeldung als `output`. `GET /state/:id` liest die Zeile direkt (404 falls unbekannt), inkl. `path`-Feld. `GET /paths` liefert `{ paths: string[] }` – nur die Namen aus `config.paths` (`listPathNames()`), nicht die Dateisystem-Pfade.
  - **`GET /files/:pathName`** (`handleGetHostedNames`) liefert `{ hosted: string[] }` – nur die Namen aus `paths[].hosted` des per `pathName` aufgeloesten Eintrags (`listHostedNames()`, 404 falls `pathName` unbekannt).
  - **`GET /files/:pathName/:hostedName`** (`handleGetHostedEntry`) loest den `HostedEntry` per `resolveHostedEntry()` auf (404 falls `pathName`/`hostedName` unbekannt). Bei `type: "file"`: prueft `existsSync`+`isFile()` (404 falls die Datei nicht mehr existiert), dann `sendFileDownload()` (streamt per `createReadStream().pipe(res)`, `Content-Type` aus einer kleinen eingebauten `extname()`→MIME-Tabelle (`MIME_TYPES`, Fallback `application/octet-stream`), `Content-Disposition: attachment; filename="<basename>"`, `Content-Length` aus `statSync`). Bei `type: "path"`: prueft `existsSync`+`isDirectory()` (404 falls nicht mehr vorhanden), listet dann per `readdirSync(path, { withFileTypes: true })` **nur direkte Dateien** (`dirent.isFile()`, keine Unterordner, nicht rekursiv) als `{ files: string[] }`.
  - **`GET /files/:pathName/:hostedName/:fileName`** (`handleGetHostedFile`) nur gueltig wenn der `HostedEntry` `type: "path"` ist (sonst 404 – ein `type: "file"`-Eintrag hat keine Unterdateien); baut `filePath = resolve(join(resolve(entry.path), fileName))` und verifiziert **vor** jedem Dateizugriff, dass `filePath` innerhalb des Verzeichnisses liegt (`filePath === directory || filePath.startsWith(directory + sep)`, sonst `400`) – Pfad-Traversal-Schutz. Ueber Node's `new URL()`-Parsing (WHATWG-Dot-Segment-Removal) kann ein `..`-Segment ohnehin nie unveraendert als eigenes URL-Segment beim Server ankommen (empirisch verifiziert), die Pruefung ist bewusstes Defense-in-Depth fuer diesen Datei-Download-Endpunkt und kein toter Code fuer ein unmoegliches Szenario. Danach `existsSync`+`isFile()`-Check (404) und `sendFileDownload()` wie oben.

  Jeder Request (Erfolg wie Fehler, GET wie POST) wird zusaetzlich in `t_access_log` protokolliert (Methode, Pfad, finaler Status-Code, bei POST der rohe Body-Text) – das ist eine eigene Tabelle, getrennt von `t_commands`. `-p, --port` (Default `8787`) steuert den Listen-Port; `SIGINT`/`SIGTERM` schliessen Server und DB sauber. Der Prozess läuft im Vordergrund (kein Daemonizing – die offene Listening-Socket hält den Node-Event-Loop ohnehin am Leben). Beim Start (`server.listen`-Callback) druckt `printEndpoints()` einmalig alle Endpunkte auf stdout (`POST /`, `POST /<agent>` je Eintrag aus `config.agents`, `POST /task/<task>` je Eintrag aus `config.tasks`, `GET /state/:id`, `GET /paths`, `GET /files/:pathName`, `GET /files/:pathName/:hostedName`, `GET /files/:pathName/:hostedName/:fileName`). Danach loggt `handleRequest()` jeden einzelnen Request zusätzlich zum DB-Eintrag auch auf stdout (`<ISO-Timestamp> <METHOD> <path> -> <statusCode>`).
- **SQLite via `node:sqlite` statt `better-sqlite3`:** `src/db.ts` nutzt Node's eingebautes `node:sqlite` (`DatabaseSync`, seit Node 22.5, in Node 24 ohne Flag/Warnung nutzbar, `@types/node` deckt es ab). Bewusst **nicht** `better-sqlite3` (obwohl populärer/reifer), weil das ein natives Addon (`.node`-Binary) ist, das `esbuild` nicht in die Single-File-`cl.bundle.js` inlinen kann – das haette die gesamte "ein deploytes File reicht"-Architektur gebrochen. `node:sqlite` bleibt im Bundle als externes `import`/`require('node:sqlite')` stehen und wird zur Laufzeit von Node selbst aufgeloest, unabhaengig vom Ausführungsort (empirisch verifiziert: Bundle enthaelt `node:sqlite` als String, keine gebündelten Binaries). WAL-Modus ist aktiviert (`PRAGMA journal_mode = WAL`). Tabellen: `t_access_log` (Autoincrement-ID, Timestamp, Method, Path, Status-Code, Body) und `t_commands` (UUID-PK, agent, model, command, path, status, output, exit_code, created_at, updated_at) – `path` ist der ueber `resolvePath()` aufgeloeste Dateisystem-Pfad (cwd des `claude`-Prozesses), nicht der im Request uebergebene Name.
- **`databaseDirectory` in `config.json`:** wird beim Serverstart via `mkdirSync(..., { recursive: true })` angelegt, falls nicht vorhanden; SQLite-Datei liegt als `commands.db` (+ `-wal`/`-shm` im WAL-Modus) darin. Wie alle anderen `config.json`-Felder lokal-first mit Embedded-Fallback aufgeloest (funktional identisch, da der Wert ohnehin nur ein String ist).
- **Linting:** ESLint (Flat Config, `eslint.config.js`) mit `typescript-eslint` `strictTypeChecked` + `stylisticTypeChecked`, typisiert nur für `src/**/*.ts` (eigenes `project`). `eslint.config.js` und `scripts/*.mjs` laufen nur mit `js.configs.recommended` (kein Type-Checking nötig). Für `src/**/*.test.ts` ist zusätzlich `@typescript-eslint/no-floating-promises` deaktiviert (eigener Override-Block in `eslint.config.js`) – `node:test`s `test(name, fn)` gibt bewusst eine nicht ge-awaitete Promise zurück, die der Test-Runner selbst nachverfolgt.
- **Formatierung:** Prettier, per `eslint-config-prettier` von ESLint-Stylistik entkoppelt.
- **Tests (`node:test` + `tsx`, kein Vitest/Jest):** `npm test` = `tsx --test 'src/**/*.test.ts'` (via `pretest` laufen vorher `generate-version`/`generate-context-bundle`, da Tests `src/generated/embedded-context.ts` importieren). Bewusst kein zusätzliches Test-Framework – `node:test`/`node:assert` sind Node-Builtins (kein weiterer Dependency-Fussabdruck), `tsx` ist ohnehin schon Dev-Dependency und stript TypeScript direkt (kein separater Kompilierschritt fürs Testen). `node:test`s `mock.module()` ist in dieser Node-Version nicht zuverlässig nutzbar (empirisch geprüft) – daher **keine** Modul-Mocks, stattdessen drei Test-Strategien je nach Modul-Charakter:
  1. **Reine Funktionen direkt unit-getestet:** `parseConfig`, `listAgents` (`src/config.ts`), `buildClaudeArgs`, `buildSystemPrompt` (`src/launch.ts`) – synthetische Inputs, keine Seiteneffekte.
  2. **Lokal-first/Embedded-Fallback via Test-Seam:** `getRootDir()` in `src/config.ts` liest `process.env.CL_ROOT_DIR` (Default: echter Repo-Root wie bisher) – nur für Tests gedacht, im Normalbetrieb ungesetzt und damit wirkungslos. `src/test-support/fixture-config.ts` (`createFixtureRoot()`/`createEmptyFixtureRoot()`) baut temporäre `config.json`+`contexts/*.md`-Fixtures; darüber werden `loadConfig()`/`resolveAgent()`/`resolveContext()` sowohl im "lokale Dateien vorhanden"- als auch im "keine lokalen Dateien → embedded" Fall real durchlaufen (Embedded-Fall vergleicht gegen den echten `EMBEDDED_CONFIG`/`EMBEDDED_CONTEXTS`-Import).
  3. **Echte Subprozesse statt Mocks für alles, was `claude` spawnt:** `src/test-support/mock-claude.ts` (`createMockClaude()`) schreibt ein ausführbares Node-Script namens `claude` in ein Temp-Verzeichnis, das seine `argv` als JSON + Marker auf stdout schreibt (robust gegen Newlines/Anführungszeichen im System-Prompt, da JSON-serialisiert) und konfigurierbare Output-Chunks mit Delay + Exit-Code liefert; `pathWithMock()` haengt dessen Verzeichnis vorn an `PATH`. Damit sind `runHeadlessCommand()` (`src/launch.test.ts`), `cl server`s POST-Endpunkte (`src/server.test.ts`) und die volle CLI (`src/index.test.ts`, via `src/test-support/run-cli.ts` – spawnt `node_modules/.bin/tsx src/index.ts <args>` als echten Kindprozess) End-to-End getestet, ohne echte `claude`-Aufrufe/API-Kosten.
  - `src/db.ts` wird direkt gegen echte temporäre SQLite-Dateien getestet (kein Mock nötig, `node:sqlite` ist synchron und schnell).
  - `src/server.ts`: `startServer()` gibt (seit diesem Refactor) `{ port, ready, close() }` zurück statt `void` – `port` ist ein Getter auf den tatsächlich gebundenen Port (relevant bei `port: 0` fürs OS-Port-Assignment in Tests), `ready` resolved nach `server.listen()`, `close()` räumt Listener + DB sauber auf. Tests treffen den Server per echtem `fetch()`.
  - `src/index.ts` wird **nie direkt importiert** (weder in Tests noch sonstwo) – das Modul hat Top-Level-Seiteneffekte (eager `loadConfig()` mit `process.exit(1)`, `program.parseAsync(process.argv)`), ein Import würde also sofort die echte CLI-Logik gegen die Test-Runner-`argv` ausführen. Getestet ausschliesslich per Subprozess.
  - Nebenbei durch die Tests gefundener Bug: `cl server --port 0` wurde von der eigenen Validierung (`port <= 0`) abgelehnt, obwohl Port `0` ("beliebiger freier Port", OS-Konvention) gültig ist – Fix: `port < 0`.

## npm-Scripts

- `npm run dev` – führt `src/index.ts` direkt via `tsx` aus (kein Compile).
- `npm run build` – `tsc`-Compile nach `dist/`.
- `npm run deploy` – bündelt (`esbuild`) und kopiert nach `~/.local/bin/cl`.
- `npm run release` – `build` + `deploy` nacheinander.
- `npm test` – `tsx --test 'src/**/*.test.ts'` (mit `pretest`-Hook fuer die Generatoren).
- `npm run lint` / `npm run format` – ESLint / Prettier.

**`Makefile`:** duenner Wrapper um alle `package.json`-Scripts (`make generate-version`, `make generate-context-bundle`, `make dev`, `make build`, `make deploy`, `make release`, `make test`, `make lint`, `make format`) – jedes Target ruft 1:1 `npm run <script>` (bzw. `npm test` fuer `test`) auf, keine eigene Logik. `pre*`-Hooks (`predev`/`prebuild`/`pretest`) sind nicht als eigene Targets abgebildet, da `npm` sie beim Aufruf des jeweiligen Haupt-Scripts ohnehin automatisch mitausfuehrt.

## Feature-Implementierungsstatus

Siehe `FEATURES.md`. Aktuell umgesetzt:

- CLI-Grundgerüst mit `--help`/`--version` – `src/index.ts`.
- Deployment-Pipeline (`dev`/`build`/`deploy`/`release`) – `package.json`, `scripts/deploy.sh`, `scripts/generate-version.mjs`.
- Config/Context-System (lokal-first mit Embedded-Fallback) – `config.json`, `contexts/`, `src/config.ts`, `scripts/generate-context-bundle.mjs`.
- `cl [agent]` startet Claude Code interaktiv mit dem `main`-Agent (ohne Argument) oder einem benannten Agent aus `agents[]` (Model, System-Prompt aus Contexts, `acceptEdits`-Permissions) – `src/launch.ts`, `src/index.ts`, `src/config.ts`.
- `cl --help` listet alle Agents aus `config.json` mit ihrer `description` dynamisch auf – `src/index.ts`.
- `cl <model> [agent]` (Subcommands `haiku`/`h`, `sonnet`/`s`, `opus`/`o`, `fable`/`f`) überschreibt das Model aus `config.json` für den gewählten Agent – `src/index.ts`, `src/launch.ts`.
- Startup-Validierung: CLI bricht sofort ab, wenn ein `agents[].name` mit einem Model-Command/Kurzform kollidiert – `src/config.ts`, `src/index.ts`.
- `-h, --headless [prompt]` (auf Root-Command und allen Model-Subcommands) startet headless statt interaktiv; ohne Wert wird der Prompt interaktiv über stdin abgefragt – `src/index.ts`, `src/launch.ts`.
- `cl server` – HTTP-Server, exposed alle Agents als headless POST-Endpunkte (`POST /`, `POST /:agent`, je mit Pflichtfeld `path` im Body zur Auswahl des Arbeitsverzeichnisses aus `config.json`s `paths[]`) mit Live-Output-Tracking + Status-Abfrage (`GET /state/:id`) sowie `GET /paths` (listet nur die konfigurierten Pfad-Namen), protokolliert in SQLite (`t_access_log`, `t_commands`) unter `config.json`s `databaseDirectory` – `src/server.ts`, `src/db.ts`, `src/config.ts`, `src/index.ts`, `openapi.json`.
- `GET /files/:pathName`, `GET /files/:pathName/:hostedName`, `GET /files/:pathName/:hostedName/:fileName` – geben `config.json`s `paths[].hosted[]` (`{ name, path, type: "path" | "file" }`) frei: erste Route listet die hosted-Namen eines Pfad-Eintrags, zweite laedt bei `type: "file"` direkt herunter bzw. listet bei `type: "path"` die darin liegenden Dateien, dritte laedt eine einzelne Datei aus einem `type: "path"`-Verzeichnis herunter (inkl. Pfad-Traversal-Schutz) – `src/server.ts`, `src/config.ts`, `openapi.json`.
- `cl server -P, --paths-file <file>` – überschreibt `config.json`s `paths` für den Serverlauf vollständig durch den Inhalt einer externen JSON-Datei der Form `{ "paths": [...] }` – `src/config.ts` (`loadPathsOverride`/`parsePathsOverride`/`applyPathsOverride`), `src/index.ts`, `src/server.ts`.
- Test-Suite (`npm test`, 82 Tests): reine Unit-Tests fuer Validierung/Arg-Building, Fixture-basierte Tests fuer lokal-first/Embedded-Fallback, Mock-`claude`-Subprozess-Tests fuer `runHeadlessCommand`/`cl server`/die volle CLI, direkte SQLite-Tests – `src/*.test.ts`, `src/test-support/`.
