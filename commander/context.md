# Kontext: commander

## Aufbau eines Projektes

Siehe `~/.claude/CLAUDE.md` ("Aufbau eines Projektes") – gilt hier unverändert: `FEATURES.md` (alle Features vollständig, selbstpflegend), `.gitignore` (Android-spezifisch, siehe unten), `context.md` (diese Datei, immer aktueller Stand ohne History), `CLAUDE.md` (Ausnahmen von globalen Regeln).

## Zweck

Native Android-App (Kotlin/Compose), Fernsteuerungs-Client für `cl server` aus dem übergeordneten `claude-cli`-Repo (`../src/server.ts`, `../openapi.json`). Eigenständiges Gradle-Projekt (`rootProject.name = "Commander"`, `applicationId`/`namespace = com.wafflehq.commander`), aufgesetzt per `/base-project`-Skill aus der WaffleHQ-Basisvorlage.

## Architektur-Entscheidungen

- **Basis:** AGP 8.9.0, JVM 17, `compileSdk 35`, `minSdk 26`, `targetSdk 35`, Jetpack Compose Material 3, Single-Activity (`MainActivity`), Compose Navigation, Hilt DI, Room, DataStore Preferences, 5-Hue-Ramp-Theme (`ui/theme/`) – aus der Basisvorlage übernommen. `compileSdk`/AGP wurden bewusst **nicht** angehoben.
- **Tastatur-Insets:** `MainActivity` aktiviert `enableEdgeToEdge()`, daher resized das System das Fenster bei geöffneter Tastatur nicht selbst. `Modifier.imePadding()` sitzt zentral auf der Root-`Surface` in `MainActivity.kt`, dadurch weichen alle Screens (u. a. `ui/run/RunAgentScreen.kt`, `ui/tickets/TicketDetailScreen.kt`, `ui/login/LoginScreen.kt`, `ui/setup/SetupScreen.kt`, `ui/settings/config/ConfigScreen.kt`, `ui/settings/contexts/ContextEditScreen.kt`, `ui/feedback/FeedbackListScreen.kt`) der Tastatur einheitlich aus, ohne dass jeder Screen einzeln `imePadding()` setzen muss.
- **Gradle-Wrapper `8.11.1`**, **Kotlin `2.2.21`**/**KSP `2.2.21-2.0.5`**/**Room `2.8.4`**/**Hilt `2.58`**/**`hiltNavigationCompose 1.3.0`**: siehe Begründung der Versionsgrenzen in `CLAUDE.md`. `ui/navigation/HiltViewModels.kt` kapselt den deprecated `androidx.hilt.navigation.compose.hiltViewModel()`-Aufruf hinter einem eigenen `hiltViewModel()`; alle Screens importieren diesen statt der `androidx`-Variante direkt.
- **`com.squareup.okhttp3:okhttp:5.3.2`**, **`mockwebserver3:5.3.2`** (Test), **`kotlinx-serialization-json:1.7.3`**, **`io.mockk:mockk:1.13.12`** (Test, für `ConnectionGateViewModelTest`s `SettingsRepository`-Fake – Konstruktor braucht einen echten `Context`, daher nicht per Hand fakebar).
- **Kein `androidx.security:security-crypto`:** TOTP-Secret wird über `data/crypto/KeystoreCipher.kt` (AES-256-GCM, Android-Keystore) verschlüsselt, nicht über `EncryptedSharedPreferences` (seit `1.1.0-beta01` deprecated).
- **TOTP-Client (`data/totp/TotpGenerator.kt`):** Clean-Room-Kotlin-Implementierung von RFC 6238/4226, bit-exakt kompatibel zu `../src/totp.ts`.
- **Auto-Discovery (`data/discovery/NetworkDiscovery.kt`):** `/24`-Subnetz-Scan gegen `GET /status`, `raceFirstMatch()`/`subnetHosts()` als reine, testbare Funktionen getrennt vom Android-spezifischen `localIpv4Address()`. Die eigene IP wird explizit über `ConnectivityManager.allNetworks`/`getNetworkCapabilities()` von dem Netzwerk mit `TRANSPORT_WIFI` gelesen (`wifiIpv4Address()`), **nicht** über das erste „up"-Interface aus `NetworkInterface.getNetworkInterfaces()` (Fallback `firstNonLoopbackIpv4Address()` nur falls kein Wi-Fi verbunden ist) – sonst kann bei gleichzeitig aktivem Mobilfunk/VPN (oder wenn Android wegen fehlendem Internet auf dem LAN das Mobilfunknetz als „aktives" Netzwerk führt) das falsche Subnetz gescannt werden und „Automatisch suchen" findet trotz erreichbarem Server nichts, obwohl die manuelle IP-Eingabe funktioniert. Erfordert `ACCESS_NETWORK_STATE`-Permission (Manifest).
- **API-Client (`data/api/ClServerApi.kt`):** Dünner OkHttp-Wrapper. Unauthentifizierte Methoden nehmen Host/Port explizit entgegen (Pairing/Login). Authentifizierte Methoden lesen die aktuelle `Connection`/`Session` aus `ConnectionSource`, senden `Authorization: Bearer <JWT>`. **Kein** `getPaths()`/`getPathCommands()`: `GET /manifest` liefert Agents + Pfade (inkl. Commands/Hosted-Einträgen) gebündelt. `getCommands(pathName, limit?, offset?)` (`GET /commands/<pathName>?limit=&offset=`) liefert eine Seite des Command-Verlaufs dieses Pfads (`CommandList`: `commands` (neueste zuerst) + `total`/`limit`/`offset`/`hasMore`, Server-Default `limit=5`) – Grundlage für den paginierten „Verlauf"-Screen (siehe unten). `stopCommand(id)` (`POST /state/<id>/stop`) beendet einen laufenden Command serverseitig (SIGTERM), Antwort `CommandAccepted`; der Endstatus `"stopped"` kommt separat über `streamState`/`getState`. Downloads streamen direkt in eine Zieldatei, Zieldateiname aus `Content-Disposition`. Fehler einheitlich als `ApiException(httpCode, message)`.
- **Live-Output per SSE (`ClServerApi.streamState(id): Flow<CommandState>`):** Liest `GET /state/:id/stream` zeilenweise über `response.body!!.source().readUtf8Line()` (kein SSE-Client-Package, reines Okio), emittiert ein `CommandState` pro `"data: "`-Zeile (Kommentarzeilen wie `: heartbeat` werden übersprungen), der Flow endet normal, sobald der Server die Verbindung schließt. Eigener `streamingClient` (OkHttp, `readTimeout = 0`, da die Verbindung bis zum Abschluss des Commands offen bleibt) statt des Standard-Clients mit 30s-Timeout. Der komplette Aufruf (`execute()` + Zeilen-Loop) läuft in einem `try`/`catch (IOException)`, das jede rohe `IOException`/`SocketException` (z. B. abrupt geschlossener Socket bei Netzwerkwechsel oder Server-Neustart mitten im Stream) in eine `ApiException` übersetzt – ohne dieses Mapping würde eine solche Exception unbehandelt durch die `viewModelScope`-Coroutine laufen und die App crashen, statt den Polling-Fallback auszulösen. `CommandDetailViewModel` sammelt diesen Flow im `init`-Block; wirft er eine `ApiException`, bevor ein Endstatus (`!= "running"`) ankam (z. B. ein Proxy ohne Streaming-Unterstützung), fällt der `init`-Block auf denselben Polling-Loop (`GET /state/:id` alle 2s) zurück, den es vorher exklusiv gab – reine Additiv-Erweiterung, kein Verhaltensunterschied für den Nutzer außer saubererer Updates. Ein `ApiException` **innerhalb** dieses Polling-Loops (z. B. kurzer Netzwerkausfall im Hintergrund) setzt nur den Fehlerbanner (`uiState.error`), beendet die Schleife aber **nicht** – erst ein echter Terminalstatus (`status != "running"`) tut das; sonst würde ein einziger transienter Fehler den Screen dauerhaft auf "Fehler" einfrieren, bis der Nutzer ihn über den Verlauf neu öffnet (neue ViewModel-Instanz).
- **Login/Session:** JWT-basiert (2h gültig, `data/connection/ConnectionRepository.kt`, `Session`/`AuthSession`), `ui/login/LoginScreen.kt` fragt den 6-stelligen TOTP-Code ab und tauscht ihn gegen ein Token. `ConnectionGateViewModel` (`ui/navigation/`) kombiniert den Session-Status **und** `SettingsRepository.selectedProjectName` zu einem `GateState` (`NoConnection`/`NeedsLogin`/`Ready(hasSelectedProject: Boolean)`) und bestimmt so den Navigations-Startpunkt.
- **Sliding-Session-Refresh (`ClServerApi.kt`):** `SessionWriter`-Interface (`data/connection/ConnectionRepository.kt`, vormals `SessionInvalidator`) hat neben `clearAuthSession()` jetzt auch `saveAuthSession(token, expiresAt)`, damit `ClServerApi` neu ausgestellte Tokens selbst persistieren kann. Zwei Auslöser für `POST /auth/refresh`: (1) `execute()` prüft nach jedem erfolgreichen authentifizierten Response, ob der Request einen `Authorization`-Header trug und nicht selbst `/auth/refresh` war, und startet dann `scheduleBackgroundRefresh()` – fire-and-forget in einem eigenen `CoroutineScope(SupervisorJob() + Dispatchers.IO)`, gedrosselt auf max. einen Versuch pro Minute (`lastRefreshAttemptAt`, `@Volatile`). (2) `refreshSessionIfLoggedIn()` (public suspend fun) wird explizit von `ConnectionGateViewModel.refreshTokenOnForeground()` aufgerufen, das wiederum über einen `LifecycleEventObserver` (`ON_START`) in `AppNavHost.kt` bei jedem Vordergrund-Wechsel getriggert wird – ignoriert die Minuten-Drosselung, tut aber nichts ohne gültige Session. Beide Pfade laufen über `performRefresh(session)`, das Fehler (`ApiException`) still schluckt (best effort, nächster Versuch bei der nächsten Gelegenheit).
- **Ausgewähltes Projekt (`data/settings/SettingsRepository.kt`):** DataStore-Key `selected_project` – merkt sich den zuletzt gewählten `manifest.paths[].name` app-weit, bis der Nutzer ihn über das Projekt-Dropdown im Hub ändert oder sich abmeldet (`SettingsViewModel.disconnect()` löscht ihn mit). Zusätzlich DataStore-Key `usage_banner_expanded` (`booleanPreferencesKey`, Default `true`) für den Ein-/Ausklapp-Zustand des Nutzungslimits-Banners im Hub.
- **Dev-Kontexte (`data/context/DevContextRepository.kt`, `data/db/AppDatabase.kt`):** Room-Tabelle `dev_context` (`id`/`name`/`value`) – frei anlegbare Prompt-Textbausteine, verwaltet unter Settings → Kontexte. Beim Agent-Start (`ui/run/RunAgentScreen.kt`) zeigt ein `FlowRow` von `AppChip(variant = ChipVariant.Filter)` einen Chip pro Preset, Mehrfachauswahl über `RunAgentUiState.selectedContextIds: Set<Long>`/`RunAgentViewModel.onContextToggled(id)`; alle gewählten Werte werden in Anzeigereihenfolge per `"\n\n"`-Join vor den Prompt gehängt (`ui/run/RunAgentViewModel.kt#buildAgentCommand(contextValues: List<String>, prompt)`), bevor `POST /<agent>` aufgerufen wird. Sind Kontexte gewählt, ist der Prompt optional (leerer Prompt → nur die Kontext-Werte werden gesendet), `RunAgentViewModel.start()` erzwingt einen Prompt nur, wenn keine Kontexte gewählt sind. `AppDatabase` ist auf `version = 2`, `fallbackToDestructiveMigration(dropAllTables = true)` (`di/AppModule.kt`) – keine eigene Migration nötig, da rein lokale Presets eines persönlichen Tools.
- **Input-/Output-Copy (`ui/command/CommandDetailScreen.kt`):** Icon-Button neben dem Command-Text (in `CommandSummary`) kopiert `state.command` (String `command_detail_input_copied`), Icon-Button neben dem „Output"-Titel kopiert `state.output` (String `command_detail_output_copied`) – beide per `LocalClipboard` in die Zwischenablage, Bestätigung per `Toast`, gemeinsame lokale `copyToClipboard()`-Hilfsfunktion in `CommandDetailScreen`.
- **Laufenden Command stoppen (`ui/command/CommandDetailScreen.kt`/`CommandDetailViewModel.kt`, `ClServerApi.stopCommand()`):** Solange `state.status == "running"`, zeigt die Seite einen „Befehl stoppen"-Button (`AppButton`, Role Error/Tonal, deaktiviert waehrend `uiState.stopping`); Tap oeffnet `AppConfirmDialog` („Befehl stoppen?"), Bestaetigen ruft `POST /state/<id>/stop` auf (`CommandAccepted`-Response). Der Server sendet SIGTERM an den Subprozess; der resultierende Endstatus `"stopped"` kommt wie jeder andere Statuswechsel ueber den laufenden SSE-Stream/Polling-Fallback zurueck – kein optimistisches Client-Update. Ein Fehlschlag (z. B. Command bereits abgeschlossen, HTTP 409) zeigt das bestehende Fehler-Banner.
- **Datei-Downloads/APK-Install (`data/download/HostedFileDownloader.kt`):** Downloads landen unter `getExternalFilesDir(DIRECTORY_DOWNLOADS)`, Öffnen/Teilen über `FileProvider`. Endet der tatsächliche Dateiname (aus `Content-Disposition`) auf `.apk` (reine Funktion `isApkFileName`, testbar ohne Android-Kontext), zeigt `ui/components/ApkActionDialog.kt` (`AlertDialog`) statt eines automatischen Öffnen-Intents die Wahl zwischen „Installieren" (`installIntent()`: `ACTION_VIEW`, MIME `application/vnd.android.package-archive` – Android zeigt dabei bei Bedarf selbst den "Unbekannte Quellen erlauben"-Dialog, `REQUEST_INSTALL_PACKAGES`-Permission im Manifest, kein Runtime-Request nötig), „Teilen" (`shareApkIntent()`: `ACTION_SEND` + `Intent.createChooser()`, damit die APK an andere Apps/Geräte weitergegeben werden kann) und „Löschen" (Bestätigungsdialog, entfernt Datei + Cache-Eintrag). Tap außerhalb des Dialogs bricht ohne Aktion ab, ohne die Datei zu löschen. Nicht-APK-Dateien laufen weiterhin automatisch über `openOrInstallIntent()` (= `shareIntent()`, `ACTION_VIEW` mit dem vom `ContentResolver` ermittelten MIME-Typ) ohne Dialog. Verwendet sowohl in `ui/downloads/DownloadsScreen.kt` als auch in `ui/command/CommandDetailScreen.kt`.
- **„Gebaut am"-Anzeige pro APK (`ui/downloads/DownloadsScreen.kt`, `ui/command/CommandDetailScreen.kt`):** Jede `type: "file"`-Zeile (Top-Level und aufgeklappte `path`-Einträge in `DownloadsScreen.kt`, Schnellzugriff-Downloads in `CommandDetailScreen.kt`) zeigt gut sichtbar (`bodyMedium`/`onSurface`, nicht `onSurfaceVariant`) den `apk_build_time`-String ("Gebaut am %1$s") mit `formatTimestamp(entry.timestamp)` (`dd.MM.yyyy HH:mm`, Geräte-Zeitzone, `ui/history/TimestampFormat.kt`). Dafür geben `DownloadsViewModel.expandedHostedFiles` (`Map<String, List<HostedFileEntry>>`, vorher nur Dateinamen) und `CommandDetailViewModel.hostedFiles` (`List<ManifestHostedEntry>`, vorher nur Namen) jetzt die vollständigen Einträge statt bloßer Namen-Strings weiter, damit der vom Server gelieferte `timestamp` nicht mehr verloren geht.
- **Versionierter Download-Verlauf (überlebt Dialog-Dismiss/App-Neustart, `data/download/DownloadHistoryRepository.kt`):** Jede erfolgreich heruntergeladene Datei (nicht nur APKs) merkt sich `HostedFileDownloader` als `DownloadVersion(key, timestamp, downloadedAt, filePath)` in DataStore (Store `download_history`, ein `stringPreferencesKey` mit JSON-serialisierter `List<DownloadVersion>`, `decodeDownloadVersions()`/`encodeDownloadVersions()`), Schlüssel `"<pathName>::<hostedName>"` bzw. `"<pathName>::<fileName>"` für Dateien innerhalb eines aufgeklappten `path`-Eintrags; `timestamp` ist der beim Download bekannte Server-Stand (`ManifestHostedEntry.timestamp`/`HostedFileEntry.timestamp`, `null` falls unbekannt), `downloadedAt` der Geräte-Zeitpunkt des Downloads (`Instant.now().toString()`). `DownloadHistoryRepository.recordVersion()` haengt neue Versionen an bestehende desselben Keys an (reine Funktion `applyDownloadVersion()`, testbar ohne DataStore) statt sie zu ueberschreiben und behaelt hoechstens `MAX_DOWNLOAD_VERSIONS_PER_KEY = 3` Versionen pro Key; ueberzaehlige (aelteste) Versionen werden zurueckgegeben und von `HostedFileDownloader.runDownload()` von der Platte geloescht. Innerhalb eines Keys ist die Speicherreihenfolge immer alt→neu (die neueste Version ist stets die letzte fuer diesen Key), das treibt sowohl die "aktuellste Version"-Suche (`resolvePendingInstall()`) als auch die Sortierung im Verlauf-Screen ohne fragile String-Zeitvergleiche. Vor jedem Tap auf Download/Install-Icon holen `DownloadsViewModel`/`CommandDetailViewModel` **zuerst live** den aktuellen Timestamp (`GET /manifest` bzw. `GET /files/<pathName>/<hostedName>` für Dateien in einem aufgeklappten `path`-Eintrag) statt sich auf zuletzt geladene Listen zu verlassen, dann prüft `resolvePendingInstall(pathName, identity, currentTimestamp)` die neueste gespeicherte Version: stimmt ihr Timestamp mit dem aktuellen überein (oder ist einer der beiden `null`), liefert ein Cache-Treffer die Datei ohne erneuten Download; weicht er ab, bleibt die alte Version unangetastet im Verlauf erhalten und `resolvePendingInstall` gibt `null` zurück, sodass neu heruntergeladen und als zusätzliche Version angehängt wird (kein Löschen mehr bei Versionswechsel – das übernimmt ausschließlich die 3-Versionen-Kappung). Ist die Datei der neuesten Version von der Platte verschwunden (z. B. manuell gelöscht), entfernt `resolvePendingInstall` nur diesen einen Eintrag (`deleteVersion(key, filePath)`). `HostedFileDownloader.pendingInstalls: Flow<List<DownloadVersion>>` filtert dafür zusätzlich auf APK-Dateinamen und je Key auf die neueste Version – treibt unveraendert das Install- statt Download-Icon in `ui/downloads/DownloadsScreen.kt`/`ui/command/CommandDetailScreen.kt`, für Nicht-APKs bleibt das Icon Download (nur der Netzwerk-Download wird bei Cache-Treffer übersprungen). Der Installieren/Teilen/Löschen-Dialog öffnet sich **nur** durch einen bewussten Tap auf das Icon, nie automatisch. Erst „Löschen" (`deletePendingInstall()`) entfernt Datei und den zugehörigen Verlaufseintrag; Dialog-Dismiss (`consumeDownloadedFile()`) lässt ihn unangetastet.
- **Download-Verlauf-Screen (`ui/downloads/DownloadHistoryScreen.kt`, `DownloadHistoryViewModel.kt`, Route `DOWNLOAD_HISTORY = "downloads/{pathName}/history"`):** Erreichbar über einen Button oben auf `DownloadsScreen`. Liest `DownloadHistoryRepository.versions` direkt (nicht über `HostedFileDownloader.pendingInstalls`, da dort auf APKs gefiltert wird), `groupDownloadHistory()` (reine Funktion) filtert auf den aktuellen `pathName`, gruppiert nach Datei-Identity und sortiert jede Gruppe neueste-zuerst. Pro Gruppe eine `AppCard` mit bis zu drei Versionszeilen (Server-Zeitstempel + `downloadedAt`, Öffnen-Icon über `downloader.openOrInstallIntent()`, Löschen-Icon mit `AppConfirmDialog` → `downloader.deletePendingInstall(pathName, identity, file)`, entfernt genau diese eine Version). Leerzustand zeigt `download_history_empty`.
- **Download-Fortschritt:** `ClServerApi.downloadHostedEntry()`/`downloadHostedFile()` lesen den Response-Body in 8-KB-Chunks über Okio und melden alle ~150ms sowie am Ende `DownloadProgress(bytesDownloaded, totalBytes, bytesPerSecond, etaSeconds)` (`data/api/DownloadProgress.kt`) über einen `onProgress`-Callback; `totalBytes` ist `null` ohne `Content-Length`-Header. `DownloadProgressTracker` glättet die Geschwindigkeit über ein 2-Sekunden-Fenster (älteste Samples verworfen) und leitet die ETA aus Restbytes/Geschwindigkeit ab (`null` ohne bekannte Gesamtgröße oder bei Geschwindigkeit 0). `HostedFileDownloader` hält den Fortschritt in `downloadStatus: StateFlow<DownloadStatus?>` (`DownloadStatus(phase, progress)`, `DownloadPhase = DOWNLOADING|VERIFYING|INSTALLING|OPENING`): `DOWNLOADING` während des Streamings, `VERIFYING` nach Abschluss (prüft `file.exists() && length() > 0`, wirft sonst `ApiException`), abschließend `INSTALLING` bei `.apk`-Dateien bzw. `OPENING` bei allen anderen. `DownloadsViewModel`/`CommandDetailViewModel` reichen `downloadStatus` unverändert durch und halten zusätzlich lokal `downloadingName: String?` (welcher Eintrag/welche Datei gerade auf diesem Screen angezeigt wird); `clearDownloadStatus()` läuft bei Fehlern und beim Konsumieren der heruntergeladenen Datei. `ui/downloads/DownloadProgressIndicator.kt` (geteilt zwischen `DownloadsScreen.kt` und `CommandDetailScreen.kt`) zeigt einen `LinearProgressIndicator` (determinate bei bekannter Gesamtgröße, sonst indeterminate) plus Text mit Prozent/Geschwindigkeit/ETA (`ui/downloads/DownloadProgressFormat.kt`) oder dem reinen Phasen-Label außerhalb der `DOWNLOADING`-Phase.
- **Download läuft im Hintergrund weiter (`data/download/HostedFileDownloader.kt#startDownload`, `DownloadTarget.kt`, `DownloadForegroundService.kt`, `CommanderApp.kt`):** Der eigentliche Netzwerk-Download läuft nicht mehr in `viewModelScope`, sondern in `HostedFileDownloader`s eigenem, prozessweiten `downloadScope` (`CoroutineScope(SupervisorJob() + Dispatchers.IO)`) – ein Tab-Wechsel oder das Zerstoeren des ViewModels bricht ihn dadurch nicht ab. `startDownload(pathName, hostedName, fileName, timestamp)` prueft zuerst `activeTarget: StateFlow<DownloadTarget?>` (app-weiter Lock: **ein** Download gleichzeitig, unabhaengig vom Screen), liefert `false` ohne zu starten falls bereits einer laeuft, setzt sonst `activeTarget` synchron und startet `runQueuedDownload()` im `downloadScope`, das nach Abschluss `downloadOutcome: StateFlow<DownloadOutcome?>` (`Success(target, file)`/`Failure(target, message)`) setzt und `activeTarget` wieder auf `null`. `DownloadsViewModel`/`CommandDetailViewModel` rufen `startDownload()` statt der Download-Suspend-Funktionen direkt auf, gleichen beim Erstellen (`resumeActiveDownload()`) ihren lokalen `downloadingName` mit einem bereits laufenden `activeTarget` desselben `pathName` ab (Rueckkehr auf den Screen waehrend ein Download noch laeuft) und sammeln `downloadOutcome` (`observeDownloadOutcome()`, gefiltert auf `target.pathName`) um `downloadedFile`/`error` zu setzen und den Eintrag per `consumeDownloadOutcome()` zu quittieren. `CommanderApp` beobachtet `activeTarget` prozessweit und startet bei einem Wechsel zu nicht-`null` `DownloadForegroundService` (`startForegroundService`, Manifest-Typ `dataSync`, Permissions `FOREGROUND_SERVICE`/`FOREGROUND_SERVICE_DATA_SYNC`/`POST_NOTIFICATIONS`, Laufzeit-Anfrage in `MainActivity` ab API 33): der Service haelt per `startForeground()` eine dauerhafte Fortschritts-Notification (Kanal `download_notification_channel_name`, Icon `ic_notification_download`, Titel/Text aus `activeTarget`/`downloadStatus`) und beendet sich selbst, sobald `activeTarget` wieder `null` wird – das haelt den Prozess am Leben, auch wenn die App minimiert wird.
- **Navigation (`ui/navigation/AppNavHost.kt`, `Routes`):** Linearer Fluss ohne Hamburger-Menü. `NoConnection → SETUP`, `NeedsLogin → LOGIN`, `Ready` ohne gemerktes Projekt `→ PROJECT_SELECT` (reine Namensliste aus `manifest.paths`, Tap wählt + persistiert), `Ready` mit gemerktem Projekt `→ PROJECT_HOME` (Hub: Projekt-Dropdown zum Wechseln oben, Zahnrad zu Settings, darunter neun Einträge: **Entwicklung** (optisch hervorgehoben als eigene `AppCard`/`ProjectHomeDevelopmentCard` mit Primary-Akzentfarbe, `Icons.Outlined.SmartToy`-Icon und Untertitel, `ui/projecthome/ProjectHomeScreen.kt`), **Befehle**, **Downloads**, **Tickets**, **Verlauf**, **Feedback**, **Sammlung**, **Statistik**, **Remote-Sitzungen** (die übrigen acht als schlichte `SettingsListRow`)). Jeder Bereich ist ein eigener, fokussierter Screen ohne Querverweise auf die anderen:
  - `COMMANDS` (`ui/commands/`): nur `path.commands`, Tap öffnet einen `AppConfirmDialog` („Befehl ausführen?"), erst nach Bestätigung wird ausgeführt und `COMMAND_DETAIL` geöffnet.
  - `DOWNLOADS` (`ui/downloads/`): nur `path.hosted` (Ordner aufklappbar, Datei-Download inkl. Installieren/Teilen-Dialog für APKs).
  - `AGENTS` (`ui/agents/`): Liste `manifest.agents` (`command`+`description`), Tap öffnet `AGENT_RUN`.
  - `AGENT_RUN` (`ui/run/RunAgentScreen.kt`, in-place aus dem früheren "Agent starten" umgebaut): Agent und Pfad sind fix (aus der Navigation, nur Anzeige, keine Dropdowns mehr), dazu Prompt-Feld (nur Pflicht, wenn kein Kontext gewählt ist), optionales Kontext-Dropdown (`data/context`) und optionales Model-Dropdown (Default vorausgewählt).
  - `TICKETS`/`TICKET_DETAIL` (`ui/tickets/`): wie zuvor, aber `pathName` ist jetzt **Pflichtparameter** – der frühere globale, pfadlose Modus (alle Pfade gemischt, Pfad-Dropdown beim Anlegen) wurde entfernt, da nicht mehr erreichbar. `TICKET_DETAIL` hat zusätzlich einen Play-Button (Bestätigungsdialog inkl. Agenten-Auswahl aus `manifest.agents`, Default `cl dev` falls vorhanden) – schickt `claudeInstruction` per `POST /<agent>` los, navigiert danach zu `COMMAND_DETAIL` und schließt das Ticket (`PATCH status=done`) erst nach erfolgreichem Start des Commands. `TicketListViewModel.createTicket()` ruft `POST /tickets/<pathName>` auf und laedt die Liste danach neu (`refresh(showLoading=false)`) – der Server legt das Ticket sofort im Status `"generating"` an (leere Felder) und fuellt es im Hintergrund; solange ein Ticket der geladenen Liste im Status `"generating"` ist, pollt `ensureGeneratingPoll()` die Liste jede Sekunde neu (`ui/tickets/TicketListScreen.kt`s `TicketRow` zeigt dafuer einen Spinner statt Kategorie-Text). Kein client-seitiger Platzhalter mehr (`data/tickets/TicketCreationRepository.kt` wurde entfernt).
  - `HISTORY` (`ui/history/HistoryScreen.kt`): Liste aus `GET /commands/<pathName>?limit=&offset=` (neueste zuerst), serverseitig in 5er-Schritten paginiert (`HISTORY_PAGE_SIZE = 5`, `ui/history/HistoryViewModel.kt`). `HistoryUiState` haelt zusaetzlich zu `commands`/`loading`/`error` noch `loadingMore`/`hasMore`; `loadMore()` haengt per `getCommands(pathName, limit = 5, offset = commands.size)` eine weitere Seite an (dedupliziert per `id` gegen bereits geladene Eintraege, falls sich das Fenster zwischen zwei Aufrufen durch neu hinzugekommene Commands verschoben hat). Der Poll alle 3s (`POLL_INTERVAL_MS`, `while (isActive) { refreshLoadedWindow(); delay(...) }`) fragt **nicht** immer nur Seite 1 ab, sondern das aktuell geladene Fenster (`limit = commands.size.coerceAtLeast(5), offset = 0`) und ersetzt `commands` 1:1 durch das Ergebnis – dadurch bleiben bereits nachgeladene Seiten und die Scroll-Position erhalten (kein Reset auf 5 Eintraege bei jedem Tick), waehrend Status-Aenderungen laufender Commands und neu hinzugekommene Eintraege ganz oben trotzdem live ankommen. Ein Fehler bei einem Hintergrund-Poll oder bei `loadMore()` setzt nur `error`, laesst die bereits geladene Liste unangetastet (kein harter Reset der Ansicht). `HistoryScreen.kt` haengt bei `hasMore || loadingMore` einen zusaetzlichen `item(key = "load-more")` ans Ende der `LazyColumn`: ein „Mehr laden"-`AppButton` (`ButtonVariant.Tonal`) bzw. ein `CircularProgressIndicator` waehrend `loadingMore`. Tap auf einen Eintrag öffnet dieselbe `COMMAND_DETAIL`-Seite wie „Befehle"/„Entwicklung". `ui/history/TimestampFormat.kt` formatiert `createdAt` (`formatTimestamp`, reine Funktion) und die Laufzeit aus `createdAt`/`updatedAt` (`formatDuration`, reine Funktion, `java.time.Duration`/`Instant` – "Ns" unter einer Minute, "Nm NNs" unter einer Stunde, sonst "Nh NNm"); beide Werte werden in der Zeile unter dem Command-Text kombiniert (`history_row_meta`). `formatTimestamp`/`formatDuration` werden auch in `ui/command/CommandDetailScreen.kt` (`CommandSummary`) genutzt, um Startzeitpunkt (`command_detail_started_at`, aus `createdAt`) und Laufzeit (`command_detail_duration`) unter dem Command-Text anzuzeigen. Solange `state.status == COMMAND_STATUS_RUNNING`, tickt ein lokaler `LaunchedEffect`-Loop (`delay(1_000)`) `now: Instant` sekündlich hoch und die Laufzeit wird aus `createdAt` bis `now` berechnet – echter Live-Timer, unabhängig davon, ob der Server gerade `updatedAt` per Output-Chunk aktualisiert. Nach Abschluss friert die Anzeige auf `formatDuration(createdAt, updatedAt)` ein. Status-Pill-Rolle (`statusRole`/`historyStatusRole`, je einmal in `CommandDetailScreen.kt`/`HistoryScreen.kt`): `completed` → Success, `running` → Warning, `stopped` → Neutral, sonst (`failed`) → Error. **Agenten-Läufe neu starten:** `CommandState.isRetryable()`/`retryAgentCommand()` (`data/api/ApiModels.kt`) grenzen auf nicht-laufende, nicht-Pfad-Commands und nicht-Hook-Läufe ein (`status != "running"` und `agent` beginnt weder mit `"path-command:"` noch mit `"hook:"`) – also `completed`/`failed`/`stopped` gleichermaßen, nicht nur Fehlschläge – bzw. rekonstruieren aus dem gespeicherten `agent` (`"main"` oder ein Agentenname) den `ManifestAgent.command`-Wert (`"cl"`/`"cl <name>"`), den `AGENT_RUN` als Navigationsparameter erwartet. `onLastAgentFinish`-Hook-Läufe (Server-seitig als `agent: "hook:<pathName>:onLastAgentFinish"` in `t_commands` erfasst, siehe `../context.md`) erscheinen dadurch ganz normal in `HISTORY`, aber ohne Wiederholen-Icon (kein freier Prompt zum Retry, wie bei Pfad-Commands). Ein Wiederholen-Icon (`AppIconButton`) erscheint nur bei retrybaren Einträgen; Tap navigiert über `Routes.agentRun(pathName, agentCommand, prefillPrompt = command.command)` zu `AGENT_RUN` (neuer optionaler Query-Parameter `?prefillPrompt=`), `RunAgentViewModel` seeded damit `RunAgentUiState.prompt` – abgeschickt wird weiterhin nur durch manuellen Tap auf „Starten".
  - `FEEDBACK` (`ui/feedback/FeedbackListScreen.kt`, **projektgebunden**, `pathName` aus der Navigation): Liste aus `GET /feedback/:pathName` (authentifiziert, serverseitig auf diesen Pfad gefiltert), pro Eintrag Bearbeiten (Inline-`AppTextField` mit `minLines = 4`, also mehrzeilig/textarea-artig fuer laenger werdendes Feedback, + Speichern → `PATCH /feedback/:id`), Löschen (`AppConfirmDialog` → `DELETE /feedback/:id`) und "In Ticket umwandeln" (Dialog mit Projekt-Dropdown aus `manifest.paths`, vorausgewaehlt ist das aktuelle Projekt sofern in der Liste enthalten, ruft `createTicket(pathName, text)` gefolgt von `deleteFeedback(id)`). Ist `entry.section` gesetzt (z. B. `"periodical-debug.apk"`, automatisch von `app-getter` mitgeschickt), zeigt die Zeile eine zusaetzliche Zeile `feedback_section` darunter; analog `feedback_context` fuer `entry.context` (Freitext, von `app-getter` mit APK-Name + Zeitstempel vorbelegt). `entry.path` (welchem Projekt der Server das Feedback anhand der `section` zugeordnet hat) wird nicht extra angezeigt, da er bereits implizit aus dem Screen-Kontext folgt. Kein Erstellen aus der App heraus – `POST /feedback` ist für externe, unauthentifizierte Absender gedacht (z. B. `app-getter`-Nutzer oder ein Web-Formular).
  - `COLLECT` (`ui/collect/CollectScreen.kt`, **projektgebunden**, `pathName` aus der Navigation): ein einzelner Button "Sammeln" (`POST /collect/:pathName` ohne Body, sammelt nur die diesem Projekt zugeordneten `collection`-Eintraege). Zeigt das Ergebnis (`CollectSummary`) als Erfolgs-/Fehler-Banner pro Eintrag.
  - `STATS` (`ui/stats/StatsScreen.kt` + `StatsViewModel.kt`): projektgebunden, lädt einmalig `GET /stats/<pathName>` (`ClServerApi.getStats(pathName, hours)`, `ProjectStats`-Modell) und zeigt vier `StatRow`-Zeilen (Label + Wert in einer `AppCard`): laufende Agents, Agents im festen 24h-Fenster (`formatWindowHours()` rundet `windowHours: Double` auf eine Ganzzahl-Anzeige, falls glatt), letzter Debug-/Release-Build-Zeitpunkt (`formatTimestamp` aus `ui/history/TimestampFormat.kt`, sonst `stats_no_build_yet`). Kein Live-Polling, kein Refresh-UI.

Versionsverlauf/Rollback.
  Entfernt: das frühere Dashboard (`ui/home/`, alle Agents/Pfade/Tickets-Zähler/Verlauf gemischt auf einer Seite), `ui/pathdetail/` (Commands+Hosted+Agent-Start+Tickets-Button gemeinsam auf einer Seite), `ui/components/AppDrawer.kt`/`AppHeader.kt` (Hamburger-Menü, dadurch toter Code). Der frühere rein lokale, client-seitige Command-Verlauf (`data/history/*`) wurde nicht wiederhergestellt – der neue `HISTORY`-Screen ist stattdessen server-seitig backed (`GET /commands/<pathName>`, `t_commands`), damit der Verlauf App-Neustarts überlebt und alle Clients denselben Stand sehen.
- **Nutzungslimits-Banner (`ui/components/UsageLimitBanner.kt`, `ProjectHomeViewModel.kt`):** Zeigt `GET /usage`s `UsageLimit[]` (`label`, `percentUsed`, `resetsAt`) als Karte ganz oben im Projekt-Hub, vor dem Projekt-Dropdown – eine Zeile pro Limit mit Label, Prozentwert, `LinearProgressIndicator` (Farbe ueber `usageRoleFor(percentUsed)`, reine Funktion: `< 70` Neutral, `70-89` Warning, `>= 90` Error) und darunter dem Reset-Zeitpunkt (`R.string.usage_banner_resets_at`, zeigt `limit.resetsAt` unveraendert durch – bereits ein fertig formatierter Text vom Server, z. B. `"Aug 27, 5:40pm (Europe/Berlin)"`, siehe `../src/usage.ts`). Die Karte hat einen klickbaren Header (Titel + `ExpandLess`/`ExpandMore`-Icon), der die Limit-Zeilen ein-/ausklappt (`animateContentSize()`); der Zustand wird ueber `SettingsRepository.usageBannerExpanded` (DataStore, `booleanPreferencesKey`, Default `true`) persistiert und ueber `ProjectHomeViewModel.usageBannerExpanded`/`onUsageBannerExpandedChanged()` an den Screen gebunden. Datenquelle ist `data/usage/UsageRepository.kt` (`@Singleton`, ein `StateFlow<List<UsageLimit>>`, `suspend fun refresh()` fragt `GET /usage` ab und schluckt `ApiException` still) statt eines eigenen API-Aufrufs im ViewModel – so teilen sich alle Aufrufer denselben zuletzt geladenen Stand. `ProjectHomeViewModel` sammelt diesen `StateFlow` in sein `uiState` und pollt zusaetzlich alle 60s per `usageRepository.refresh()` (`USAGE_POLL_INTERVAL_MS`, eigene `while (isActive) { ...; delay(...) }`-Schleife analog zu `HistoryViewModel`, unabhaengig von der einmaligen `refresh()` fuer `availablePaths`). Zusaetzliche Trigger fuer ein frischeres Limit, ohne auf den 60s-Poll zu warten: `ConnectionGateViewModel.refreshUsage()` beim App-Vordergrund-/Hintergrundwechsel (`ON_START`/`ON_STOP`, `ui/navigation/AppNavHost.kt`s Lifecycle-Observer, neben `refreshTokenOnForeground()`) sowie ein `usageRepository.refresh()` direkt nach jedem erfolgreichen Abfeuern eines Commands/Agents (`CommandsViewModel.runCommand()`, `RunAgentViewModel.start()`, `TicketDetailViewModel.play()` – jeweils nur bei Erfolg, nicht im Fehlerfall). Ein Fehler beim Laden wird still ignoriert (best effort, wie `ClServerApi.performRefresh()`) – die Anzeige ist informativ und soll nichts blockieren. Ohne Limits (noch nicht geladen) rendert `UsageLimitBanner` nichts.
- **DI (`di/AppModule.kt`, `di/BindsModule.kt`):** `AppDatabase`/`DevContextDao` über `@Provides` (Room). Alle übrigen Repositories nutzen reine `@Inject`-Konstruktor-Injection.
- **Remote-Sessions (`ui/remotesessions/*`, `data/api/ClServerApi.kt#getRemoteSessions`/`startRemoteSession`):** Projektgebunden, `pathName` aus der Navigation. `RemoteSessionsScreen`/`RemoteSessionsViewModel` laden beim Öffnen `GET /paths/<pathName>/remote-sessions` (`ClServerApi.getRemoteSessions()`) und zeigen jede aktive Session (interaktiv wie Hintergrund) als `AppCard`-Zeile (Name, Status-Pill, Typ inkl. Kurz-ID bei Hintergrund-Sessions ueber `RemoteAgentSession.isBackground()`, Startzeitpunkt ueber `formatTimestamp`). Ein optionales Namensfeld + Button ruft `POST /paths/<pathName>/remote-sessions` (`ClServerApi.startRemoteSession()`) auf, zeigt die zurueckgelieferte Kurz-ID als Erfolgs-Banner und laedt die Liste danach neu. Kein Live-Polling (Start ist synchron, die Liste wird nur bei Bedarf neu geladen).
- **Server-Konfiguration (`ui/settings/config/*`):** Editiert die servergehaltene `config.json` remote über `../FEATURES.md`s `/config`-Endpunkte. `ClServerApi.getConfig()`/`putConfig()`/`getConfigVersions()`/`getConfigPointer()`/`setConfigPointer()` (letztere beiden per neuem `authedPut()`-Helper) transportieren die Config bewusst als rohes `kotlinx.serialization.json.JsonElement` statt als eigene Kotlin-Datenklasse – das Server-Schema (Agents/Tasks/Paths/Permissions/…) muss so clientseitig nicht dupliziert/synchron gehalten werden. `ConfigScreen`/`ConfigViewModel`: lädt `GET /config`, zeigt sie in einem mehrzeiligen `AppTextField` pretty-printed zum Bearbeiten, „Speichern" validiert lokal per `Json.parseToJsonElement` (verhindert einen Server-Roundtrip bei kaputtem JSON) und ruft dann `PUT /config`; ein `warning` (z. B. bei geändertem `databaseDirectory`) erscheint als eigenes Banner. `ConfigVersionsScreen`/`ConfigVersionsViewModel`: Liste aller Versionen (`GET /config/versions`) + aktiver Zeiger (`GET /config/pointer`, `null` = eingebettete Version), Tap auf eine inaktive Zeile fragt per `AppConfirmDialog` nach und aktiviert sie danach (`PUT /config/pointer`) – Hot-Reload auf dem Server, kein Neustart der App nötig.
